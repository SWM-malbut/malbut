# 실기기 관찰형 스모크 테스트 (SWM25-255)

실행 진입점은 이 디렉터리의 **`smoke.sh` 하나**다. 내부 Python도 파일 안에 포함되어
별도 설치·빌드 없이 기존 ROS 메시지, ManagerClient, 음성 경로, 낙상 상태·기록을 사용한다.
Manager·Agent·추적·낙상 알고리즘과 기존 우선순위는 수정하지 않는다.

## 실행 전

- 로봇의 최신 빌드로 Bringup을 실행한다. 웹 경로라면 `cloud.launch.py`만 켜지 말고
  웹에서 Bringup 준비까지 시작한다. 이 스크립트는 **실행 중인 구성에 연결할 뿐**
  Bringup·드라이버·모델을 중복 실행하거나 다른 프로세스를 종료하지 않는다.
- 음성·사람추적·낙상 모듈이 모두 실행되어 있어야 한다. 다른 미션이나 미해결 낙상 사건이
  있으면 먼저 정상적으로 정리한다. 테스트 실행기가 기존 사건을 임의로 처리 완료시키지 않는다.
- 사람이 지켜보고 수동 정지 수단을 확보한다. 이동 공간을 비우고 카메라 앞에는 검사자만 둔다.
  낙상은 실제로 넘어지지 말고 안전하게 연출한다.
- **테스트 기기·보호자/알림 수신 대상을 사전에 확인한다.** 실제 API 과금, 영상 전송,
  사건 기록과 알림이 발생할 수 있다. `--test-alerts-confirmed`는 이 확인에 대한 실행자의
  명시적 동의이지, 수신 대상을 격리해 주는 기능이 아니다.

```bash
# 계획만 출력. ROS·API·이동 요청 없음.
bash /home/ubuntu/ros2_ws/src/malbut/smoke.sh

# 읽기 전용 준비 검사. 안내 TTS·모델 로딩·미션 요청·API 요청 없음.
bash /home/ubuntu/ros2_ws/src/malbut/smoke.sh --check

# 실제 검사. 시작 시 이 한 번의 명시적 허용 후 중간 승인 없이 진행.
bash /home/ubuntu/ros2_ws/src/malbut/smoke.sh --execute --test-alerts-confirmed
```

ROS Humble와 기존 `install/setup.bash`, `install/malbut_test/local_setup.bash`를 자동으로
읽는다. `robotrc`, `.zshrc`, 키 파일은 source하지 않으며 키를 새로 입력받지 않는다.
실제 API는 이미 실행된 기존 노드의 설정·키를 사용한다. 모델이나 패키지를 다운로드하지 않는다.
다른 workspace는 `MALBUT_SMOKE_WORKSPACE`, 관측용 Python은 `MALBUT_SMOKE_PYTHON`으로
지정한다. 관측용 Python에는 `rclpy`와 빌드된 Malbut 패키지가 필요하지만 추론 환경은 불필요하다.

별도 설정으로 Bringup을 실행했다면 같은 DB/낙상 설정 경로를 전달한다.

```bash
bash smoke.sh --execute --test-alerts-confirmed \
  --conversation-db /실제/음성대화.sqlite3 \
  --fall-config /실제/fall_runtime.json \
  --follow-seconds 30
```

## 자동 진행 순서

1. **준비**: 실제 센서 데이터·TF, Manager/음성 연결과 RPC 응답, 유휴/정지 상태,
   현재 FallFlow·영상·감지 동의, 기존 DB 스키마를 확인한다. 유휴 Nav2가 inactive인 것은
   정상이다. STT의 `ready`만 보지 않고 Agent의 발화 수신, Manager의 음성 중계,
   TTS의 실제 수신·제어 경로와 필요한 Action 서버가 발견됐는지 확인한다.
   RGB·Depth 추가 구독은 모델·Nav2 초기화를 기다리는 동안 만들지 않으며,
   센서 확인 구간에만 만들고 성공·실패와 관계없이 즉시 해제한다.
2. **음성대화**: 안내에 따라 호출어를 부르고 테스트 중이라고 말한다. 답변 후 안내에 따라
   방금 무엇을 한다고 했는지 묻는다. 각 STT 발화 ID와 답변·재생 ID를 연결하고,
   읽기 전용 대화 DB에서 같은 요청의 `openai` provider와 응답 ID를 확인한다.
   고정 안내, 진행 알림, mock, API 실패 시 대체 답변을 실제 LLM 성공으로 세지 않는다.
   안내가 끝나는 순간 먼저 도착한 답변도 보존한다. 사용자가 안내를 끊고 대답했다면
   실제 안내 정지와 해당 대화의 완료를 확인하며, 그것만으로 TTS 오류로 판정하지 않는다.
3. **사람추적**: 안내 후 기본 3초 준비 시간을 두고 기존 Manager에 `follow_person`을
   한 번 요청한다. 실제 target-visible 피드백을 받은 뒤 기본 30초 관찰한다.
   음성 정지를 말하면 조기 종료할 수 있고, 시간이 지나면 자동 취소한다.
   최종 CANCELED, 잔여 미션 없음, 유휴 복귀와 신선한 odom의 저속 상태를 확인한다.
   음성 정지를 안 했다면 그 부가 검사는 `NOT_TESTED`로 기록한다.
4. **낙상**: 안내 후 안전한 상황을 연출한다. 기존 감지·Cloud 판단·이동/재관찰·질문 절차를
   그대로 관찰하며 안내를 중간에 끼워 넣지 않는다. 질문하면 괜찮다고 답한다.
   새 사건에 연결된 실제 Cloud 결과, 최종 처리, DB의 완료 기록과 정리를 확인한다.
   정책상 질문 없이 종료하는 경로라면 질문은 NOT_REQUIRED다. 감지 상태나 발행된 종료 명령만으로
   완료 처리하지 않는다. VLM은 실제 기존 원격 provider이며 재시도 정책도 변경하지 않는다.
   일반적인 주기 Cloud 분석 진행은 준비 실패가 아니다. 별도 Topic의 Cloud 결과보다
   Agent 종료 메시지가 먼저 처리돼도 해당 결과와 완료 기록을 제한 시간 내 기다린다.
5. **대화 복귀**: 안내에 따라 호출어를 부르고 테스트가 끝났으니 인사해 달라고 말한다.
   일어날 때 같은 사건을 다시 확인하는 기존 FallFlow 동작은 먼저 종료까지 기다린다.
   실제 LLM 응답·TTS 완료와 잔여 미션이 없음을 확인한다.
6. **일괄 관찰 평가**: 자동 결과를 먼저 출력한 뒤 마지막에 한 번만 키보드로 평가한다.
   Enter는 관찰한 항목 전부 정상, `2,4:질문이 안 들림`은 해당 항목 실패와 메모,
   `q`·EOF·입력 시간 초과는 미평가다. 중간에 Enter를 누를 필요가 없다.
   TTS 청취 품질은 안내·대화·낙상 질문을 듣고 마지막에 함께 평가한다.

## 실패·중단 및 결과

- 자동 검사의 실패를 사람의 Enter로 덮어쓰지 않는다. 미실행·미평가가 있으면 전체 PASS가 아니다.
- 각 단계에 제한 시간이 있다. 실패 이후의 기능은 연쇄 실행하지 않고 정리 후 결과를 출력한다.
  고정 시간 잠들었다가 다음 기능을 실행하는 방식이 아니라 실제 조건을 확인한다.
  대기가 길어지면 현재 기다리는 조건과 경과 시간을 터미널에 표시한다.
- 느린 초기화·전환과 실제 기능 실패를 구분하도록 대기 예산을 분리한다.
  `--ready-timeout`은 준비 조건별 기본 180초, `--rpc-timeout`은 읽기 전용 RPC의 발견·응답과
  기록 확인에 각각 기본 30초, `--transition-timeout`은 활성화·정상 유휴 복귀에 기본 120초다.
  `--turn-timeout`은 발화·안내에 90초, `--fall-timeout`은 낙상 단계에 240초,
  `--cleanup-timeout`은 취소 결과·재생 정지 확인에 60초다. 이후 실제 유휴 복귀도 별도로 확인한다.
  이 값은 조건별 최대 대기이며 고정 지연이나 전체 실행 시간 상한이 아니다.
  시간 초과를 감추려고 이동 Goal·안내·API 요청을 재전송하지 않는다.
- ROS graph 조회는 0.5초 간격으로 제한한다. 실제 odom·낙상 상태의 신선도 기준은
  완화하지 않고, RPC 응답과 최종 Action 결과도 계속 확인한다.
- Ctrl+C/SIGTERM 시에도 bounded cleanup 중 ROS를 계속 처리한다. 테스트의 추적 Goal과 안내
  재생 ID만 취소하고, 테스트 낙상 단계에서 새로 관측한 사건만 기존 정지 경로로 중단한다.
  이전 사건, 다른 사람이 요청한 미션, 드라이버와 Bringup은 임의 종료하지 않는다.
- 늦은 Goal 접수, API 응답 미확인, 실제 TTS worker 종료 미확인, 유휴 복귀 실패는 성공으로
  감추지 않는다. 정리를 확인하지 못하면 다음 이동을 하지 않고 수동 정지를 요청한다.
  **SIGKILL·전원/네트워크 단절은 정리 실행을 보장할 수 없고, 이 스크립트는 물리 비상정지가 아니다.**
- 결과는 기본 `~/.local/state/malbut/smoke/<실행 회차>/report.json`과 터미널에 남는다.
  디렉터리 0700·파일 0600이며 원문 발화·사진·음성·API 키는 저장하지 않는다.
  실제 provider 응답 ID와 사용량, 상태 코드, 관찰 메모는 포함한다.
- 실제 TTS backend를 기록한다. Piper면 로컬 TTS 검사이며 OpenAI로 몰래 바꾸지 않는다.
  worker 재생 완료는 확인하지만 TTS의 내부 API 호출 횟수와 보호자에게 알림이 실제 전달됐는지는
  현재 인터페이스만으로 검증하지 않는다. 이를 검증한 것처럼 표시하지 않는다.

| 종료 코드 | 의미 |
| --- | --- |
| 0 | 필수 자동 검사·관찰 모두 정상 (`--check`에서는 준비 검사만 정상) |
| 1 | 검사 실패 또는 실행 환경 오류 |
| 2 | 미실행·미평가 포함, 또는 잘못된 실행 인자 |
| 3 | 정리·정지를 확인하지 못함, 직접 정지 필요 |
| 130 | 사용자가 중단함. 별도 cleanup 결과도 확인 |

`--no-review`는 최종 사람 평가만 생략한다. 자동 검사가 성공해도 전체 결과는 미평가/코드 2다.
같은 사용자·ROS_DOMAIN_ID의 중복 스모크 실행은 파일 잠금으로 거절한다.
`--check`나 스모크 통과는 추적 정확도·장시간 누수·낙상 정확도의 정량 성능 인증을 의미하지 않는다.

## 개발 검증

`malbut_bringup/test/test_guided_smoke.py`는 이 파일 안의 실제 프로그램을 읽어 검사한다.
순서 뒤바뀜·중복/과거 응답·API fallback·DB 잠금·취소 완료 누락·worker 종료 누락·정리·평가와
전체 자동 순서를 대역 장치로 검증한다. `test_guided_smoke_ros.py`는 ROS가 있을 때 실제
Humble 메시지·DDS·기존 SpeechCoordinator로 별도 검증한다. 모델/API/물리 장치는 대역이다.
초기화가 145초로 늦어지는 경우, RPC 발견·응답이 각각 12·18초 걸리는 경우,
기능 활성화·유휴 전환·음성·DB 기록을 지연시키고 Cloud 결과 순서를 바꾸는 전체 흐름도 검사한다.
이 지연 재현은 부하 상황의 순서·대기 로직 검증이며 실제 CPU 포화 상태의 실기기 부하 시험은 아니다.

```bash
python3 -m pytest -q malbut_bringup/test/test_guided_smoke*.py
bash -n malbut_test/smoke.sh
```

이 개발 검증의 성공과 실제 로봇·실제 API·실제 스피커에서의 성공은 구분해야 한다.
