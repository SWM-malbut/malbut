## 3. 정한 실행 기준

| 항목 | 기준 |
|---|---|
| 영상 입력 | 640×400 RGB, 최근 5초에서 시간순 최대 12장. 한 분석 요청에 함께 전달 |
| 사람이 보일 때 주기적 확인 | 60초마다 |
| 사람이 보이다 안 보일 때 | 2분간 60초 주기를 유지한 뒤, 계속 안 보이면 5분마다 |

| 같은 사건 추가 재확인 | 최대 2회 |
| 설정 변경 권한 | 로봇 소유자만 |
| 서버 저장 후 로봇 적용 목표 | 3초 이내. 아직 실물에서 실측하지 않음 |
| 최신 설정 회신이 없을 때 | 저장 후 6초에 웹에서 ‘회신 없음’. 설정을 자동 취소하지 않음 |
| Manager ↔ VLM 상태·연결 확인 | 1초마다, 5초간 새 메시지가 없으면 끊김 처리 |
| 서버 최신 설정을 확인하지 못할 때 | 마지막 정상 확인 후 15초에 새 Cloud 전송 중단 |
| 감지 사용·영상 저장·Cloud 동의 | 서로 구분. 영상 저장 ON을 감지 ON이나 Cloud 동의로 사용하지 않음 |

상태를 1초마다 보낸다는 것은 VLM을 매초 호출한다는 뜻이 아니다.
모르는 센서값은 0으로 채우지 않는다. 실제 로봇의 이동·회전 속도 요약 연결도 남아 있다.

## 4. 이제 할 순서

### 1) 현재 실행 중인 로봇 프로그램을 서버에서 구분

- 홈캠·Manager·VLM의 이번 실행 ID를 서버에 등록하는 입력·출력과 재시작 처리를 먼저 정한다.
- 기존 장치 인증을 사용하고, 이전 실행의 늦은 회신을 현재 상태로 덮어쓰지 않도록 구현한다.
- 메시지가 늦게 도착했다는 이유나 UUID 문자열 순서로 어느 실행이 최신인지 정하지 않는다.

완료 기준: 재시작 전 회신이 와도 현재 실행과 설정 적용 상태를 바꾸지 않는다.

### 2) 현재 실행 상태를 웹까지 전달

- Manager가 받은 VLM 상태를 홈캠의 서버 통신부를 거쳐 웹에 전달한다.
- ‘서버에 저장됨’, ‘로봇에 적용됨’, ‘현재 감지 가능’, ‘Cloud 분석 성공/실패’를 구분한다.
- 로봇 연결이 끊기면 과거 성공 이력은 남기되 현재도 동작 중인 것처럼 표시하지 않는다.
- 상태 확인 때문에 시험용 Cloud 요청을 보내지 않는다.

완료 기준: VLM 중단·재시작·연결 끊김이 웹에 반영되고, 저장 성공만으로 감지 실행 중이라고 표시하지 않는다.

### 3) 실제 감지 전에 필요한 설정과 카메라 연결 확인

- 영상 저장을 꺼도, 감지와 카메라를 허용하면 카메라·YOLO-Pose 입력이 유지되는지 확인한다.
- Aurora 930의 실제 영상·depth 정렬과 촬영 시각을 확인하고, 바닥 거리·로봇 이동/회전 속도 요약을 연결한다.
  측정하지 못한 값은 `None`으로 유지한다.
- 예시 설정의 `null` 값은 2026-09-23에 로봇 테스트용 시작값으로 채웠다.
  5 fps 입력, 10초·64장·16 MiB 버퍼를 사용하며 Cloud 입력은 최근 5초·최대 12장이다.
  나머지 값과 실물 점검 순서는 [로봇 실행 준비](fall_robot_preparation.md)에 정리했다.
- 보드의 메모리·처리 속도로 검증한 뒤 값을 확정한다. 임의 기본값으로 감지를 켜지 않는다.
- Cloud 계정·키·사용 한도를 확인한다. 서버 DB 적용과 배포는 담당자와 별도로 진행한다.
- ROS 호출 권한도 설정한다. 실행 ID가 맞다는 것만으로 호출자 인증을 대신하지 않는다.

완료 기준: 녹화 설정과 감지 설정이 섞이지 않고, 실행에 필요한 설정·권한·배포 준비가 갖춰진다.

### 4) Agent 질문·답변과 웹 알림 연결

- 질문·답변 담당자와 Manager 연결 형식을 맞추고 실제 질문·응답을 연결한다.
- 연결되지 않은 Agent를 ‘사람이 무응답’인 것으로 처리하지 않는다.
- 낙상이 보였는데 괜찮다고 답한 경우에도 낙상 기록은 유지한다.
- 웹 알림은 **SWM25-188**에서 진행한다. 도움 요청·확인된 무응답·판단 불가에 따른 알림과 실제 웹 푸시 수신을 확인한다.
- 질문·답변 Agent 연동은 별도 협업 작업이며, 웹 알림 티켓이 STT/TTS 구현까지 담당한다는 뜻은 아니다.
- 최근 낙상 기록의 목록·상세 화면은 별도 작업으로 연결한다.

완료 기준: 질문 대상과 사건이 맞고, 실제 답변·무응답에 따라 기록과 알림이 구분된다.

### 5) 낙상 감지 전체 흐름 검증

- 먼저 시험용 카메라 입력·Cloud·Agent로 자동 검사를 확장한다. 실물이 없어도 진행할 수 있다.
- 이후 실제 카메라 → YOLO-Pose/주기적 Cloud → 질문·답변 → 기록 → 웹 알림까지 확인한다.
- 카메라 OFF, 동의 철회, Cloud 시간 초과·잘못된 응답, 서버 단절, 노드 재시작을 함께 시험한다.
- Jetson에서 주행·음성과 동시에 돌려 프레임 처리 속도·메모리·낙상부터 알림까지의 지연을 측정한다.
- 실제 로봇 시험은 로봇 확보 후 수행한다. 위험한 실제 낙상을 유도하는 방식은 사용하지 않는다.

완료 기준: 정상 흐름뿐 아니라 끊김·재시작·판단 불가 상황의 기록과 알림도 확인한다.

### 6) 같은 조건으로 성능 재평가

- 승인한 영상·라벨·박스와 평가 코드·프롬프트를 고정한다.
- YOLO-Pose 포착률 / VLM 단독 정확도 / YOLO-Pose 후 VLM 정확도를 다시 측정한다.
- 미호출, 모델 오판, 불필요한 알림, 호출량, 감지 지연을 따로 기록한다.
- 이미 본 합성 데이터의 개선 결과와, 새 영상·실물에서 확인한 결과를 구분한다.

VLM 평가·개선은 없애는 작업이 아니다. 앞서 비교 평가는 했고, 연결을 마친 조건에서 다시 검증해야 한다.

저장소 전체 기능의 테스트가 모두 통과했다고 주장하는 것도 아니다.
브라우저 직접 조작, 운영 DB 적용·배포, 실물 카메라, 직접 Cloud 인증,
