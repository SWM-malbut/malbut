# Pose 연결 없이 Cloud 발견으로 확인 시작

2026-09-27

## 바꾼 이유

Pose 후보는 바로 사건을 만들지만, 주기적 Cloud가 의심한 사람을 Pose에 연결하지
못하면 기존에는 발견 기록만 남았다. Manager의 확인 질문으로 이어지지 않았다.
감지 시작은 Pose 또는 Cloud 중 한 경로의 유효한 의심으로 가능해야 하며,
같은 사람·사건으로의 병합은 중복을 줄이는 별도 작업이다.

## 현재 동작

| 입력 | 처리 |
| --- | --- |
| Pose 의심 후보 | 기존 사람별 사건 생성·영상 확인 경로 유지 |
| Cloud 의심 + 확실한 Pose 연결 | 기존 사건에 반영하거나 사람별 사건 생성 |
| Cloud 의심 + 연결 불가/위치 없음/위치 오류 | 대상 미확인 장면 사건 생성·일반 확인 질문 전달 |
| 정상·판단 불가·응답 형식 전체 오류 | 낙상 의심 신호로 꾸며 사건을 생성하지 않음 |

- 미확인 사건은 `FallIncident.subject_key=None`이다. 가짜 사람 ID를 만들지 않는다.
- Manager 이벤트에는 `confirmation_scope=scene`, `subject_key=null`을 함께 전달한다.
  기존 사람별 확인은 `confirmation_scope=subject`이며 유효한 사람 ID가 필요하다.
  scope가 없는 기존 메시지는 사람별 계약으로 처리하므로, 누락된 사람 ID를 장면 확인으로
  자동 해석하지 않는다.
- 이미 받은 Cloud 판정을 사용하며 확인 시작을 위해 추가로 Cloud를 호출하지 않는다.
- Manager는 특정인을 지목하지 말고 주변에 넘어졌거나 도움이 필요한 사람이 있는지
  묻도록 Agent에 고정된 요약을 전달한다. Cloud 설명 원문을 지시문으로 전달하지 않는다.
- 같은 장면 확인이 열려 있으면 여러 미연결 발견을 그 확인에 보관한다. 각 발견의
  위치·시각·이유·발견 ID는 별도로 남긴다. 이 묶음이 같은 사람이나 같은 낙상이라는 뜻은 아니다.
- 반복 발견은 사건·질문·재확인 횟수를 늘리지 않는다. 낙상 의심에서 실제 낙상 관측으로
  근거가 강해지면 한 번 새 버전·질문을 만들 수 있다. 이미 도움 필요 상태라면 유지한다.
- 미확인 사건에 받은 도움 불필요 답변은 `unclear` 답변과 `recheck_required` 상태로 기록한다.
  응답자를 대상과 연결하지 못했으므로 실제 대상이 괜찮다고 확정하지 않는다.
- 도움 필요 답변은 해당 장면 사건을 `help_required`로 바꾸고 기존 알림 요청 경로에 전달한다.
  낙상 확정으로 바꾸거나 다른 사람의 사건에 답변을 적용하지 않는다.
- 장면 정상 판정으로 미확인 사건을 닫지 않는다. 대상 없는 사건별 `recheck`는
  `target_unidentified`로 거부하고, 주기적 Cloud 확인은 계속한다.
- 설정 철회/연결 차단 뒤의 늦은 응답, 분석 도중 이미 바뀌거나 종료된 사건의 오래된
  응답은 새 질문으로 되살리지 않는다. 용량 상한은 유지하며, 공간이 없으면 발견에
  `incident_capacity`를 기록한다.

## 검증

검증 코드는 Cloud 입력·응답을 테스트 값으로 대체한다. 실제 API 비용, 로봇 이동,
실제 음성 재생이나 보호자 알림 발송은 없다.

- 코어: Pose 없이 확인 시작, 반복·다인 발견의 질문 중복 방지, 타인의 정상/도움 불필요
  결과로 종결 금지, 도움 필요 전달, 버전 변경·설정 철회·용량 상한·SQLite 재열기.
- Manager: 명시적인 장면 scope만 수용, 일반 질문, 동일 질문 재전달 중복 방지,
  대상 ID가 없는 확인 결과도 사건·질문·실행 ID로 검증.
- 실제 ROS Topic/Action: 코어가 만든 Cloud 단독 사건 → Manager → 시험용 Agent →
  결과 Topic → 코어 왕복. 도움 필요/불필요 두 경우를 확인한다.
- 실제 ROS 영상·설정 PC 검사: Pose 후보 없이 60초 후 장면 확인·질문 이벤트·저장까지 확인한다.

저장된 다인 4개 장면 × 2개 모델 응답도 재생했다. 입력 JPEG·Pose 기록·Cloud 응답을
기존 해시와 대조했으며, 새 추론이나 API 호출 없이 현재 코어와 Manager 전달 코드를 실행했다.

| 항목 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 유효한 Cloud 의심 응답 | 7개 | 7개 |
| 사람별 사건에 연결 | 1개 | 1개 |
| 미연결 6개에서 확인 질문 전달 | 0개 | 6개 |
| 유효 응답에서 확인 질문 전달 합계 | 1개 | 7개 |
| 동일 응답 재전달로 추가된 질문 | 0개 | 0개 |

Gemma SYN045의 기존 JSON 오류 1개는 그대로 실패로 두었다. 복구해서 정답으로 세지 않았다.
7/7은 **저장된 유효 응답이 확인 질문으로 전달된 수**이며, 모델 정확도·사람 연결 정확도·
실제 음성 질문 성공률이 아니다. 이 재생은 주기 스케줄러나 Cloud 지연을 재현하지 않는다.

## 남은 제한

연결 실패는 [두 가지 경우](fall_association_cases.md)로 추가 구분한다.
유효한 Pose 관측이 없는 경우와 관측은 있지만 대상 연결을 확인하지 못한 경우를 기록하며,
두 경우 모두 위의 일반 확인 경로를 유지한다. 이 분류만으로 사람을 연결하거나 사건을 병합하지 않는다.

- 미연결 장면 사건을 특정 사람의 사건으로 자동 전환/병합하지 않는다. 확실한 동일인 근거와
  질문·답변 이전 규칙을 검증해야 한다. 이후 Pose에 사람이 보인다는 이유만으로 연결하지 않는다.
- 열린 일반 확인 하나로 반복 질문을 줄이므로, 새로운 다른 사람의 의심도 그 장면 기록에
  추가될 수 있다. 다인 상황의 재질문 간격·현장 확인/명시적 종결 운영 기준은 별도 검증이 필요하다.
- 웹 업로드 JSON은 변경하지 않았다. 원시 발견은 로컬에 남고 사건 이벤트는 기존 outbox로
  전달 가능하다. 웹의 대상 미확인 표시, 운영 서버 배포, 실제 푸시 수신은 이번 검증 범위 밖이다.
- 기록은 재시작 후 남지만 이전 질문을 자동으로 재생하지 않는다. 기존 재시작 복구 정책을 유지한다.
