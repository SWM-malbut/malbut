## 1. 승인으로 인정하는 증거

다음 조건을 모두 만족해야 승인으로 기록한다.

- SWM25-27·34·36·38·40·41의 담당자 또는 위임받은 reviewer가 작성한다.
- `SWM25-69 계약 0.4-review-candidate`와 자신이 승인하는 스토리를 명시한다.
- 입력·출력, timeout·취소, idempotency, 안전 책임과 개인정보 항목을
  검토했다고 명시한다.
- 결정이 `승인`인지 `수정 요청`인지 구분한다.
- Jira 댓글 또는 GitHub PR 댓글/review의 영구 링크를 남긴다.
- 필수 수정 요청이 하나라도 열려 있으면 해당 스토리는 승인으로 세지 않는다.

구두 동의, 메신저의 단순 이모지, 담당자가 확인되지 않는 체크 표시와
계약 버전이 없는 댓글은 승인 증거로 사용하지 않는다.

## 2. 공통 검토 체크리스트

관리자는 다음 책임 경계가 필요하다는 점을 확인했다. 아래 세부값과 시험은
SWM25-73~77 구현 전 각 실행 노드 담당자가 확정한다.

- [ ] 커스텀 ROS interface 타입과 package·이름을 구현 시 확정한다.
- [ ] 요청·응답·feedback의 세부 필드·단위를 구현 시 확정한다.
- [ ] timestamp, source와 freshness의 구체적인 임계값을 확정한다.
- [ ] timeout, 취소와 늦게 도착한 결과의 Tool별 세부값을 확정한다.
- [ ] `request_id` 또는 `tool_call_id` 중복 실행 방지 시험을 추가한다.
- [ ] LLM과 로컬 실행 노드의 안전 책임 분리를 통합 시험한다.
- [ ] 개인정보의 구체적인 보존 기간·삭제·로그 정책을 확정한다.

위 미완료 항목은 책임 경계 승인을 무효화하지 않지만 해당 물리 기능을
활성화하기 전에 반드시 닫아야 한다.

## 3. 담당 스토리별 승인 요청

### 3.1 SWM25-27 긴급 호출

반드시 확인할 결정:

- 긴급 호출은 LLM·인터넷과 무관한 로컬 경로로 시작한다.
- LLM은 긴급 판정, 연락 실행, 취소와 비상 정지 해제를 할 수 없다.
- 긴급 상태에서는 이동·촬영·따라가기를 시작하지 않는다.
- 발생·중복 억제·연락 성공·실패·취소 상태를 이벤트로 제공한다.

## 4. 승인 반영 절차

1. 담당자가 위 댓글을 자신의 Jira 스토리 또는 SWM25-69에 남긴다.
2. 계약 소유자는 결정과 영구 링크를 계약 문서의 승인 기록에 추가한다.
3. 수정 요청이면 계약과 관련 테스트 초안을 갱신하고 버전을 올린다.
4. 변경된 범위의 담당자에게만 재승인을 요청하되 공통 안전 경계 변경은
   여섯 담당자 모두에게 다시 알린다.
5. 여섯 스토리 범위가 담당자 또는 권한 있는 관리자에게 승인되고 승인
   계약의 미해결 필수 수정이 0건일 때 SWM25-69 책임 경계 정의를 완료로
   전환한다.
