# 누운 상태의 낙상 후보와 사건 재확인 결과

## 결론

평가 경로에 두 가지를 추가했다.

1. 서 있던 자세가 없어도, 누운 자세에서 머리가 아래로 이동하고 골반과의 상대
   위치가 변하면 낙상 확인 후보를 만든다. 실제 관측한 관절만 사용한다.
2. 첫 VLM 요청 이후 새 낙상 동작이나 의심 자세 소실이 생기면 같은 사건의
   새 영상을 확인한다. 앞선 요청 처리 중에는 변화를 보관하고 응답 뒤 확인한다.
   첫 응답이 정상이어도 그 뒤에 생긴 변화를 버리지 않는다.

413은 재확인 후 정상 → 낙상으로 바뀌었다. 그러나 V024는 낙상 의심 → 낙상으로
과하게 단정했다. 따라서 전체 3분류 정확도는 이전과 같다.

운영 ROS 노드·알림·웹에 연결하거나 Jetson에 배포한 변경은 아니다.

## 검증 조건

- 최종 검수 데이터 84개: 낙상 25 / 낙상 의심 25 / 정상 34.
- 최종 박스 동결 SHA256:
  `c8bbb590e9e48b88969b1610c1fa3d844ef77d8d63095352fd3d72a6eb79a03a`.
- 기존 `s + 원본 비율 유지 + 판단 조건 개선 + partial_brief` 결과를 그대로 재생했다.
  이번에는 YOLO 가중치나 모델 입력을 바꾸거나 다시 추론하지 않았다.
- 박스·라벨·사람의 판단 이유는 규칙이나 VLM 입력에 넣지 않았다.
- 이전 Gemma 첫 요청 52건은 영상·JPEG·요청 해시 일치를 확인하고 응답을 재사용했다.
  새 재확인 6건은 무료 계정 확인 후 `gemma4:31b-cloud`에 실제 호출했다.
  유료 호출·자동 재시도 없음. 모든 84개에 VLM을 새로 호출한 비교는 아니다.
- 프롬프트·온도·이미지 처리 방식은 이전과 같다. 당시까지 도착한 RGB 중 최대
  12장을 사용했다. 새 결과가 나온 뒤 유리한 프레임을 골라 다시 호출하지 않았다.
- 원본 JSON 채점과 바깥 Markdown 코드 블록만 제거한 보조 채점을 따로 보존했다.
  아래 내용 비교는 보조 채점이다. 원본 응답은 58/58 코드 블록이 있어 strict
  JSON 검증을 통과하지 못한다. 내용을 고치거나 라벨을 보정한 점수는 아니다.
- 영상당 최종 결과는 사건별 마지막 응답을 사용한다. 여러 사건이면 가장 높은
  위험 분류를 사용하고, 최신 응답 실패는 과거 정상 응답으로 덮지 않는다.
  여러 응답 중 정답과 맞는 것만 고르는 방식이 아니다.

## 재확인한 6개 영상

| 영상 | 재확인 사유 | 이전 → 재확인 | 해석 |
|---|---|---|---|
| 413 | 누운 자세의 하강 + 이후 포즈 소실 | 정상 → 낙상 | 놓쳤던 낙상 장면을 확인 |
| 423 | 누운 자세에서 추가 하강 변화 | 정상 → 정상 | 여전히 낙상을 놓침 |
| 443 | 추가 하강 변화 | 낙상 → 낙상 | 판단 유지, 호출 비용 추가 |
| 425 | 의심 포즈 소실 | 정상 → 정상 | 고양이 영상의 잘못된 포즈로 불필요한 재호출 |
| V005 | 누운 자세의 하강 변화 | 정상 → 정상 | 자발적으로 눕는 동작도 조건에 걸림 |
| V024 | 새 낙상 의심 동작 | 낙상 의심 → 낙상 | 정답은 의심, 단정이 강해지는 부작용 |

108은 기존 두 번째 요청을 같은 장면의 근거 추가로 처리해 1회만 호출한다.
이를 정상이라고 추정해서 생략한 것이 아니라, 매 관측에서 같은 위치의 머리가
확인되고 몸 자세도 반복 일치한 기존 연속성 조건에 따른 처리다.

## 413 시간 순서

| 영상 재생 기준 시각 | 처리 |
|---:|---|
| 0.833초, f010 | 첫 확인. 이 시점까지 영상만 전달 |
| 1.583초, f019 | 누운 상태에서 머리·몸 상대 위치 하강 후보 발생 |
| 2.417초, f029 | 의심 포즈를 놓침. 같은 사건의 새 근거로 추가 |
| 6.695초 | 앞선 API 완료. 두 변화를 합쳐 재확인 1회 시작 |
| 9.880초 | 추가 API 완료. 낙상으로 분류 |

두 번째 입력에는 이미 도착한 f000~f062 중 12장이 포함된다. 첫 입력을 미래
프레임으로 교체한 것이 아니며, f062까지의 영상이 도착한 뒤에 별도로 확인했다.
첫 API의 과거 실측 지연 5.861초와 새 API 실측 3.185초를 합성한 가상 재생이다.
실물에서 9.88초 걸린다는 뜻이 아니다. 낙상 시작 라벨 구간 f007~f013 기준으로는
가상 재생에서 후보까지 0.50~1.00초, 최종 답변까지 8.80~9.30초다.

새 API 6건 왕복 시간: 중앙값 3.493초 / p95 4.873초.
앞선 요청 대기·영상 추가 대기는 이 왕복 시간과 별도다.
기존 호출 도구의 `.result.json` 내 `trigger_s`는 마지막 입력 프레임 시각이다.
실제 재생상의 호출 시각은 `replay.json`의 `dispatch_time_s`, 답변 도착은
`completed_at_s`를 사용한다. 두 필드를 혼용하지 않는다.

## 호출 제한과 남은 한계

- 새 변화 뒤 0.8초를 모으고 최소 1초 간격으로 확인한다. 진행 중 호출은 사건당 1개,
  추가 확인은 최대 2회다. 같은 경고 반복은 재호출하지 않되, 새 하강 관측은 구분한다.
- 횟수 소진이나 새 RGB 부족은 확인 필요로 남긴다. 시간이 지났다고 정상 처리하지 않는다.
- 규칙은 바닥·침대 높이를 측정하지 않는다. 카메라 회전, 가려진 몸, 잘못 생성된
  포즈 관절을 완전히 배제하지 못한다. 실제 로봇 움직임·depth 연계는 실물 검증이 필요하다.
- 가만히 자는 사람의 ID 변경에 대한 보호는 제한적인 2D 관측 연속성이지 신원 인식이 아니다.
- 84개는 이미 분석한 개발 데이터다. 미검토 영상에서의 일반화 성능은 아직 모른다.
- 운영 순환 버퍼·VLM worker·알림 상태와의 연결, 호출 시간 초과 처리는 이번 실험 범위 밖이다.
  이 실험의 `complete(..., 'failed')`는 실패 콜백을 받으며 새 근거를 보존하는 것까지 검증한다.
