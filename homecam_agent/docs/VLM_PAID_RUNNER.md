# 유료 VLM 비교 실행 안내

SWM25-186 / 2026-09-26

> 2026-09-28 후속 변경: 아래의 “운영 코드 유지/미반영”은 9월 26일 평가 당시 기록이다.
> 이후 Gemma 실행 공급자의 주기 확인에 같은 native_boxes_v4 지시문과 좌표 변환을 반영했다.
> 평가용 기본 프로필·완료된 입력·과거 점수는 수정하지 않았다.
> [현재 실행부](../../malbut_agent_server/docs/fall/fall_runtime.md)에 구현과 검증 범위를 정리했다.

## 이번에 구현한 것

- 후보 13개를 회사별 API 형식으로 호출하는 코드. 실제 연결과 응답은 [9개 영상 시험 결과](VLM_PAID_PILOT9_20260926.md)에 기록.
- 같은 영상에서 마지막 5초의 RGB를 최대 12장 추출하고, 모든 모델에 같은 JPEG를 전달.
- 판정, 답변 거부, 안전 차단, 판단 불가, 형식 오류, 시간 초과를 구분.
- 요청부터 **응답 전체를 받을 때까지** 최대 20초. 자동 재시도·다른 모델로 전환하지 않음.
- 라벨별 정답 수, 낙상·의심을 정상으로 답한 수, 응답 시간, 사용량, 예상 비용 기록.
- 요청 전후 기록을 각각 저장. 실행 도중 끊겨도 이미 보낸 요청을 자동으로 다시 보내지 않음.

로봇 실행부, 기존 Gemma 평가 코드와 과거 점수는 수정하지 않았다.
이번 실행부는 **VLM 단독 비교용**이다. YOLO-Pose 후보 뒤의 평가는 아직 추가하지 않았다.
질문·답변, 로봇 이동, 웹 알림, 운영 서버와 연결하지 않는다.

## 좌표 오류 후속 수정

`normalized_boxes_v3`는 기존 `explicit_json_v2`에 좌표별 축·범위·순서 확인 지시를
추가한 평가용 조건이다. 기존 프롬프트와 채점은 유지하고, 빈 위치 목록도 별도로 센다.
`derive --prompt normalized_boxes_v3`로 원본 JPEG를 유지한 새 입력을 만들 수 있으며,
`run --model-profile low_reasoning`으로 기존 비교의 모델 옵션을 명시할 수 있다.
둘 다 실제 전송은 `--execute`를 지정하고 기존 승인·예산 조건을 충족해야 한다.

[수정 내용과 9개 진단 입력](VLM_BOX_PROMPT_V3_20260926.md)에 준비·검증 내용을 기록했다.
이후 [Gemma만 9개 재평가](VLM_BOX_V3_GEMMA9_RESULTS_20260926.md)했으나 응답 검사까지
통과한 정답 수는 늘지 않았다. 운영 프롬프트는 변경하지 않았다.

## 공식 좌표 형식 v4 진단

`native_boxes_v4`는 Google 공식 예제의 `box_2d`, 0~1000 정수 yxyx 좌표를 요청한다.
평가 전용 `native_boxes.py`에서 범위·크기를 확인하고 내부 0~1 xyxy로 고정 변환한 뒤
기존 검사를 적용한다. 잘못된 값의 단위 추측·클리핑·뒤집기나 JSON 일부 추출은 하지 않는다.
원본 응답과 변환 응답은 따로 남기며, 기본 프로필과 운영 코드는 유지한다.

[Gemma 같은 9개 실제 시험](VLM_NATIVE_BOX_V4_GEMMA9_RESULTS_20260926.md)에서는
라벨과 응답 검사를 모두 통과한 정답이 9/9개였다. 실제 박스에는 신체 일부를 빠뜨리는
사례가 남아 있어 좌표 형식 통과와 사람 위치 정확도는 구분한다. 선택 코드 테스트는 241개 통과.

이후 [Gemma·Gemini 전체 84개씩 재평가](FALL84_NATIVE_BOX_REEVALUATION_20260926.md)를
완료했다. 라벨과 응답 검사를 함께 통과한 정답은 Gemma 52→71개, Gemini 55→73개였다.
읽을 수 있는 응답에서 좌표 범위·크기 오류는 없었으나 Gemma의 중복 JSON 1건과
Gemini의 낙상·의심 → 정상 오판 2건은 남았다. 운영 코드에는 아직 반영하지 않았다.

저장 응답의 [실제 박스 위치 점검](FALL84_NATIVE_BOX_LOCALIZATION_AUDIT_20260926.md)은
`audit_paid_vlm_localization.py`로 진행했다. 정답 박스가 있는 정확한 프레임만 비교하며
없는 박스를 추정하지 않는다. 실제 사람 위치·대상 연결과 숫자 형식 통과는 구분한다.

## 9월 26일 후속 점검에서 추가한 것

실제 호출 결과와 중단한 범위는 [재평가 결과](VLM_PAID_FOLLOWUP9_20260926.md)에 기록했다.
시간 초과 후 남은 영상까지 진행한 최신 결과는
[9개 평가 완료·84개 예상 비용](VLM_PAID_TIMEOUT_CONTINUATION9_20260926.md)에 정리했다.

- `provider_error`: 공급자가 준 오류 `code`, `type`, `param`을 제한된 형식으로 기록한다.
  키나 이미지를 되돌려 줄 수 있는 오류 설명 문장은 저장하지 않는다.
- `transport_diagnostics`: 응답 헤더를 받은 시점, 첫 본문 조각을 받은 시점,
  받은 바이트 수와 중단 위치를 기록한다. 이는 모델의 첫 답변 토큰 시간이 아니다.
- `Retry-After`, 요청 ID, 호출 제한 등 허용한 응답 헤더만 보관한다.
  인증 헤더·쿠키·API 키는 보관하지 않는다.
- `low_reasoning` 평가 프로필에서 Meta와 GLM의 `reasoning_effort=low`를 명시한다.
  `baseline`은 이전 요청 옵션을 유지한다. 프로필을 바꾸면 별도 실행으로 기록한다.
- `derive_bundle()`은 이전 입력의 해시를 확인하고 이미지·라벨·영상 구간을 유지한 새
  평가 묶음을 만든다. 원본 파일을 고치거나 예전 결과를 덮어쓰지 않는다.
- `explicit_json_v2`는 평가용 프롬프트에 JSON 객체, 박스 배열과 0~1 좌표 범위를
  명시한다. 검사 기준을 느슨하게 하거나 모델 답변을 고치지 않는다.
- `--continue-after-timeout`을 지정하면 한 영상이 20초를 넘겨도 다음 영상을 진행한다.
  시간 초과 요청의 비용은 미확인으로 남기고, 요청별 예산을 계속 남겨 둔다.
  남은 예산이 부족하거나 인증·할당량 오류, 시간 초과 외의 비용 미확인 오류가 나면 중단한다.
  실패한 영상을 자동 재시도하지 않으며, 기본 동작은 기존처럼 비용 미확인 시 중단이다.
- `--request-timeout-s 60`은 응답을 더 기다려 보는 별도 시험이다. 기본값은 20초이며,
  로봇 설정은 변경하지 않는다. 실행 계획·결과에 실제 제한 시간을 기록하고,
  `response_within_20s`(전체 응답 도착), `usable_reply_within_20s`(판정을 읽을 수 있는 응답)를
  따로 남긴다. 뒤의 값이 true여도 정답을 맞혔다는 뜻은 아니다.

과거 시간 초과 5건을 같은 요청으로 한 번씩 다시 보낸 결과는
[60초 응답 대기 시험](VLM_PAID_TIMEOUT60_20260926.md)에 기록했다.

84개 비교에서는 영상 라벨과 응답 오류를 따로 확인하도록 기록을 추가했다.

- `reported_assessment`: JSON에서 읽은 모델의 영상 판정. 박스 좌표가 잘못되어도
  어떤 라벨로 답했는지는 별도로 남긴다. JSON 자체를 읽을 수 없으면 추측하지 않는다.
- `response_issue_codes`: JSON 오류, 잘못된 이미지 번호, 박스 좌표 범위·크기 오류 등을 기록한다.
- `video_label_accuracy`: 영상 라벨만 정답과 비교한 점수. 시간 초과나 읽을 수 없는 답변은
  정답으로 세지 않는다.
- 기존 `accuracy`: 영상 라벨이 맞고 응답 검사도 통과한 점수. 검사 통과가 실제 사람의
  손·발까지 박스를 정확하게 잡았다는 뜻은 아니다.

두 점수 모두 전체 호출이 끝났을 때만 전체 정확도로 표시한다. 원래 응답·좌표를 고치거나
기존 9개 점수를 덮어쓰지 않는다. 이 변경 후 평가 코드와 기존 입력·Ollama 응답 처리의
선택 테스트는 **151개 통과**했다.

평가 프로필과 새 입력 생성은 Python 실행부 및 `derive` / `--model-profile` 명령행에서
사용한다. 명령행의 기본 조건은 기존 조건이다. **운영 Cloud VLM 프롬프트는 변경하지 않았다.**

새 평가 코드 테스트는 **88개 통과**, 기존 영상 입력·Ollama 응답 처리까지 함께 선택해
실행한 검증은 **128개 통과**했다. 두 수치는 서로 다른 실행 범위이며 모델 정확도가 아니다.

## 시험용 응답으로 확인한 것

아래 명령은 키와 네트워크 없이 실행한다. 실제 Cloud 응답이나 성능 측정은 아니다.

```bash
python3 -m pytest -q homecam_agent/test/test_paid_vlm_evaluation.py
```

첫 구현 검증 결과: 새 테스트 **78개 통과**. 기존 채점·영상 입력·최종 자료 검증·
Ollama 응답 처리 테스트까지 함께 실행해 **238개 통과, 8개 건너뜀**.
건너뛴 8개는 현재 Python 환경에 `aiohttp`가 없어 실행하지 못한 기존 HTTP 테스트다.
새 HTTPS 연결부의 옵션·응답 크기 제한은 대체 HTTP 클라이언트로 확인했으며,
이때는 실제 라이브러리를 통한 통신과 유료 API 호출을 확인하기 전이었다.

유료 시험 준비 중 OpenAI의 캐시 쓰기 토큰과 Kimi의 캐시 보관 시간별 과금을 추가로
확인했다. 해당 비용을 일반 입력과 중복 계산하지 않도록 수정하고 새 테스트를 더해
**80개 통과**를 확인했다. OpenAI는 `service_tier=default`를 명시한다.

xAI Chat 응답의 별도 추론 토큰과 응답에 포함된 과금 값 처리도 보완해 **82개 통과**를 확인했다.
전용 Python 환경에 `aiohttp`를 설치한 뒤 기존 입력·채점·Ollama HTTP 테스트까지 함께 실행한
선택 검증 결과는 **163개 통과**다.

확인 항목:

- 13개 후보의 요청에 같은 지시문과 이미지가 들어감.
- HTTP 200이어도 거부 표시가 있으면 정상 판정으로 채점하지 않음.
- 안전 차단과 거부가 함께 있어도 한 요청으로 셈.
- HTTP 400·403이나 JSON 오류만으로 검열이라고 단정하지 않음.
- 공급자 표시 없이 거부 문장만 반환하면 형식 오류·검토 대상으로 보관.
- `unobservable`은 거부와 구분하고, 정답 수에 넣지 않음.
- `unobservable`의 이유도 검토 대상으로 남김. 실제로 가려져 안 보인 것인지,
  정책 거부를 이 값으로 답한 것인지 자동으로 단정하지 않음.
- 전체 호출이 끝나기 전에는 전체 정확도를 만들지 않음. 완료한 요청의 점수는 별도로 표시.
- 빠른 거부를 정상 판정 응답 시간에 넣지 않음.
- 추론 토큰을 출력 토큰에 두 번 더하지 않음. 사용량이 없으면 예상 비용은 `null`.
- 명시적인 전송 승인, 단가표, 예산, 최대 호출 수, 선택 모델들의 키 중 하나라도 빠지면 호출하지 않음.
- 예상 비용을 계산할 수 없거나 인증·할당량 문제가 생기면 다음 호출을 멈춤.
  단, 사용자가 시간 초과 후 계속 진행을 선택하면 해당 요청의 예산을 남겨 두고 다음 영상을 진행함.
- 중단된 요청은 시작 기록만 남을 수 있음. 결과가 없다고 미과금으로 간주하지 않음.

## 실제 호출 전에 할 일

1. 소규모 점검에 쓸 영상 9개를 먼저 정한다. 제안은 낙상·의심·정상 각 3개다.
2. 선택한 회사로 영상을 보내도 되는지 확인한다. 기본 비교는 허용받은 합성 영상만 사용한다.
3. API 계정·모델 사용 권한을 확인한다. 키는 대화·Git·명령행 인자로 전달하지 않는다.
4. 회사별 현재 단가와 계정 과금 방식을 확인해 단가표를 작성한다. 전체 예산과 호출 수도 정한다.
5. 단가표와 API 형식이 맞는지 소규모 호출로 확인한 뒤 84개 비교로 늘린다.

첫 실제 시험에서는 8개 모델이 9개 호출을 마쳤고, 나머지는 권한·할당량 관련 응답이나
시간 초과로 중단했다. 모델별 확인 범위와 공통 프롬프트의 형식 문제는 결과 문서에 구분했다.
오류가 나면 원래 결과를 남기고, 요청 형식을 바꾸는 실험은 새 실행으로 구분한다.

키를 읽는 환경변수는 `list` 명령으로 확인할 수 있다. OpenAI 연결은
[이미지 입력 문서](https://developers.openai.com/api/docs/guides/images-vision)와 대조했다.
다른 공급자는 [Claude](https://platform.claude.com/docs/en/build-with-claude/vision),
[Gemini](https://ai.google.dev/gemini-api/docs/image-understanding),
[Meta](https://dev.meta.ai/docs/quickstart),
[Qwen](https://www.alibabacloud.com/help/en/model-studio/vision),
[GLM](https://docs.z.ai/guides/vlm/glm-5.3-flash),
[Kimi](https://platform.kimi.ai/docs/guide/kimi-k3-quickstart),
[Grok](https://docs.x.ai/developers/models/grok-4.7) 공식 문서를 참고했다.

- Meta는 Standard `muse-spark-1.2`만 사용한다. 학습 제공 조건이 다른 Contributor로 바꾸지 않는다.
- Qwen은 싱가포르 Workspace ID가 필요하다. 다른 지역은 자동으로 선택하지 않는다.
- Kimi와 GLM에는 지원하지 않는 추론 끄기·온도 0 설정을 억지로 넣지 않는다.
- Gemma는 Ollama 직접 Cloud API `gemma4:31b`다. 기존 Mac의 인증된 Ollama 경유와 다르므로
  같은 계정·호출 한도인지 별도로 확인한다.
- 요청의 추론·출력 한도·안전 설정을 기록한다. 공급자 기본 안전 필터를 우회하거나 낮추지 않는다.

## 입력 준비와 호출 전 점검

영상 준비에는 OpenCV·NumPy·Pillow, 실제 HTTPS 호출에는 aiohttp가 필요하다.
ROS나 로컬 VLM 모델은 필요 없다. 아래 경로는 예시이며, 실제 최종 자료 위치로 바꾼다.
출력 폴더의 부모는 미리 있어야 하고, 출력 폴더 자체는 새 이름이어야 한다.
영상·응답이 Git에 섞이지 않도록 저장소 밖의 폴더만 허용한다.

```bash
python3 homecam_agent/scripts/evaluate_paid_vlm.py list

# --cases에 고른 영상 ID를 추가하면 해당 영상만 준비한다. 생략하면 84개 전체.
python3 homecam_agent/scripts/evaluate_paid_vlm.py prepare \
  --frozen /path/to/reviewed-fall84 \
  --output /path/outside/git/fall84-paid-inputs

# --execute가 없으면 키를 읽거나 영상을 전송하지 않는다.
python3 homecam_agent/scripts/evaluate_paid_vlm.py run \
  --inputs /path/outside/git/fall84-paid-inputs \
  --models gpt-6-sol gemma4:31b
```

원본 영상·라벨 해시, 추출한 프레임 번호·시각·JPEG 해시, 코드·라이브러리 버전을 저장한다.
입력 파일이나 코드가 바뀌면 그대로 이어서 평가하지 못하게 한다.
라벨은 채점할 때만 사용하고 요청에는 영상·공통 지시·영상 구간 정보만 넣는다.

현재 프롬프트는 운영 코드의 주기적 확인 형식으로 `assessment`, `explanation`, `findings`를
요청한다. 모든 모델에 같은 검사를 적용한다. 바깥 코드 블록 한 겹만 제거할 수 있으며,
판정이나 설명·박스를 고쳐서 정답으로 만들지는 않는다. 필수 항목 누락이나 서로 모순되는
발견 정보는 형식 오류로 센다. 이는 새 비교의 기준이며 과거 점수를 다시 채점하지 않는다.

## 과금 실행

기본값은 전송 안 함이다. 실제 실행에는 아래 값을 **모두** 지정해야 한다.

- `--execute --approve-upload`
- `--output`: 새 결과 폴더
- `--rates`: 확인한 모델별 단가 JSON
- `--budget-usd`: 전체 평가 예산
- `--request-reserve-usd`: 한 요청에 쓸 것으로 잡아둔 금액
- `--max-calls`: 최대 호출 수
- Qwen을 고르면 `--qwen-workspace`

단가 JSON에는 출처·확인일·USD/백만 토큰 단가를 넣는다. 예시의 `null`을 무조건 0으로
바꾸면 안 된다. 입력·출력·캐시 과금이 없는 항목만 확인 후 0으로 적는다.
GPT-6에는 `cache_write_30m` 단가가 필요하다. 캐시 쓰기 토큰은 일반 입력에서 빼고
해당 단가로 한 번만 계산한다. Kimi는 숫자로 된 캐시 과금 응답 헤더만 추가로 보관하며,
5분·1시간 쓰기 토큰 합계가 사용량과 맞지 않으면 비용을 알 수 없는 요청으로 남긴다.
xAI Chat의 답변·추론 토큰은 합산하되, 응답의 `cost_in_usd_ticks`가 있으면 이를 USD로
바꾼 공급자 과금 값을 사용한다. 토큰 예상 비용과 이 값을 다시 더하지 않는다.
구독료·세금·환율·할인·구간별 요율까지 자동 계산하는 도구는 아니며, 결과는 **예상 비용**이다.
현재 입력 길이에 맞는 가격 구간과 실제 계정 요금을 확인해야 한다.

다음 요청을 위한 금액이 예산에 남아 있을 때만 호출한다. 한 요청이 잡아둔 금액을 초과해도
이미 청구된 비용을 되돌릴 수 없으므로, 이 설정을 공급자의 결제 상한으로 보면 안 된다.
공급자 계정에도 별도로 사용 한도를 설정한다. 취소·시간 초과 요청도 과금될 수 있다.

사용량이 없거나 해석하지 못한 캐시 과금 정보가 나오면 비용을 `null`로 두고 다음 호출을
중단한다. 실패·거부 응답에 사용량이 있으면 그 비용도 합산한다.

## 결과 확인

- `run.json`: 모델, 조건, 호출 순서, 입력·코드 해시, 단가와 예산.
- `00001.started.json`: 실제 호출 전 기록. 같은 번호의 결과가 없으면 전달·과금 여부 확인 필요.
- `00001.result.json`: 공급자 표시, 답변, 판정, 실패 이유, 시간, 사용량과 예상 비용.
- `summary.json`: 모델별 완료 여부, 점수, 라벨별 오류·거부·차단, 시간, 비용.

결과 폴더는 0700, 파일은 0600으로 만든다. API 키·요청 헤더는 저장하지 않는다.
답변에는 영상에 대한 설명이 포함될 수 있으므로 결과 폴더도 비공개 자료로 취급한다.
응답 본문 전체 대신 최종 답변과 숫자 사용량·명시적인 차단 표시·원응답 해시를 보관한다.

중단된 폴더에 다시 실행하면 거절한다. 원래 요청을 지우거나 덮어쓰지 말고 공급자 사용 내역을
확인한다. 재실행이 필요하면 새 폴더로 구분하고, 가장 좋은 결과만 골라 기존 점수를 바꾸지 않는다.

`accuracy`는 그 모델의 계획한 호출이 모두 끝났을 때만 나온다.
`attempted_accuracy`는 완료한 요청만의 중간 결과다. 거부·차단·시간 초과는 분모에 포함한다.
정상 판정 응답의 속도는 `classification_latency`, 전체 요청 종료 시간은
`all_request_termination_latency`에 따로 기록한다. 낙상 발생부터 알림까지의 지연은 아니다.
