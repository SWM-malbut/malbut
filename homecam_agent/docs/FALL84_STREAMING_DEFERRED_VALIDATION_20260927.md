# 연속 RGB 입력과 GPU 추적 결과의 사건 연결 시험

2026-09-27. 실험 코드만 추가했다. 운영 노드·로봇 설정·Cloud 모델은 변경하지 않았고,
새 API 호출·영상 업로드·과금도 없었다.

## 이번에 확인한 것

저장된 RGB를 원래 촬영 간격으로 재생하면서 SAM GPU 추적을 별도 작업 스레드에서 실행하고,
완성된 결과를 실제 로컬 사건 처리 코드에 전달했다. 추론 중에도 다음 RGB·Pose가 들어오도록 했다.

테스트용 조기 발견 신호에서는 대상이 있는 8개 영상 중 7개에서 사람 ID 연결이 발생했다.
**기존 Pose 사건에 붙인 것은 1건이고, 나머지 6건은 당시 해당 사람의 사건이 없어 새로 만든 경우다.**
따라서 이를 기존 사건 병합 7건 성공 또는 실제 Cloud 연결 정확도 7/8로 쓰면 안 된다.

연결된 7건 중 기존 검수 박스가 연결 시점에 있는 3건은 같은 사람으로 확인됐다.
나머지 4건은 그 시점의 검수 박스가 없어 정답·오답을 확정하지 않았다.
영상이 끝난 뒤 늦게 도착한 결과와 카메라 OFF 뒤 끝난 GPU 결과는 연결하지 않았다.

## 데이터와 시험 조건

[앞선 GPU 시험](FALL84_GPU_DEFERRED_FOLLOWUP_20260927.md)의 영상 9개를 재사용했다.
움직임·가림 장면 6개, 다인 장면 2개, 발견 신호가 없는 정상 대조 영상 1개다.
각 영상은 24fps·123프레임으로 약 5초이며, 추가로 사용할 긴 영상은 현재 없다.

- RGB 입력은 원래 촬영 시각의 4Hz 표본과 정확한 시작 박스를 받은 프레임을 사용했다.
- Pose는 이전에 실제로 추론한 결과를 해당 RGB와 함께 재생했다. 이번에는 Pose를 다시 추론하지 않았다.
- SAM 2.1 Hiera Tiny는 RTX 3070에서 BF16으로 새로 추론했다. GPU 계산 완료를 동기화해 시간을 쟀다.
- SAM에는 이미 도착한 JPEG만 순서대로 넣었다. 전체 영상 길이나 미래 이미지 텐서를 먼저 주지 않았다.
- 촬영 시각을 결과 도착 시각으로 바꾸거나 마지막 프레임을 복제해 새 관측처럼 사용하지 않았다.
- 실제 `CloudFallMonitor`의 대상 연결 조건·최신 관측 조건·사건 처리와 SQLite 저장을 사용했다.
- ROS·실제 카메라·실제 Cloud 통신·Manager/Agent·음성·로봇 주행은 이번 시험 범위가 아니다.
  모니터의 사용 허용·연결 설정은 직접 주입했다. 실제 heartbeat 시험으로 세지 않는다.

### 왜 시험을 두 가지로 나눴나

기존 Cloud 답변은 약 5초 전체를 본 결과다. 이 답변을 영상 앞부분에 미리 넣으면
아직 찍지 않은 장면을 미리 알고 연결하는 시험이 된다. 그래서 다음 두 경우를 구분했다.

1. **조기 발견 신호 시험:** 기존 시작 박스를 테스트 입력으로만 사용하고,
   해당 프레임 수신 0.75초 뒤에 `suspected_fall / unknown` 발견 신호를 넣었다.
   기존 Cloud의 전체 영상 판단을 조기 응답으로 사용한 것이 아니다. 연속 입력 동작만 확인한다.
2. **기존 Cloud 지연 재생:** 원래 요청의 마지막 이미지가 촬영된 뒤,
   저장된 실제 응답 시간만큼 기다리고 원래 답변을 그대로 넣었다.
   원래 응답 시간은 약 3.03~9.43초여서 모든 응답이 영상 종료 후 도착했다.
   이는 현재 대상이 사라진 뒤 과거 관측만으로 연결하지 않는지 보는 대조 시험이다.

조기 시험의 대상 영상 8개, 추적 결과 155개 기준이다.

모델 최초 로딩·Pose 추론·Cloud 대기·PNG 저장·질문·알림 시간은 포함하지 않는다.
프레임별 `compute_s`는 JPEG 전처리 일부가 제외된 별도 값이므로 위 시간과 혼용하지 않는다.
이 수치는 4Hz 입력을 받는 짧은 개발 시험에서의 결과이며 전체 시스템 fps나 Jetson 성능이 아니다.

## 2. 늦은 결과와 카메라 OFF

| 조건 | 결과 |
| --- | --- |
| 기존 Cloud 답변과 실제 지연을 9개 영상에 재생 | 사람 ID 추가 연결 0건 |
| SYN059 GPU 결과를 영상 종료 후 2.2초까지 붙잡아 둠 | 오래된 관측으로 연결하지 않음 |
| SYN059 GPU 추론이 진행 중일 때 카메라 OFF | 결과는 끝났지만 `unknown_tracking_session`으로 거절 |

기존 지연 재생에서 발견이 있는 8개는 각기 장면 확인 질문 이벤트를 만들었다.
**사람에게 연결하지 못했다고 발견 자체를 버리거나 정상으로 처리한 것은 아니다.**
질문 이벤트 생성까지 확인했으며 실제 음성 질문이 나왔다는 뜻은 아니다.

카메라 OFF 시험 뒤에는 실험용 RGB 이력도 즉시 비우도록 보완하고 해당 조건을 한 번 더 실행했다.
모니터 영상 버퍼·대기열·실험용 이력이 모두 0으로 비워졌고, 실행 중이던 GPU 작업이 끝나면
SAM 상태도 해제됐다. 이미 시작한 GPU 연산을 강제로 중단한 것은 아니며, 그 결과를 사건에
반영하지 않고 대기 중인 다음 프레임 작업을 취소한 것이다.

첫 20회 시험에서 총 331프레임을 새로 추론했고, 보완한 카메라 OFF 재시험에서 1프레임을 추가로
추론했다. 21회 모두 SQLite를 닫았다 다시 열어 사건·발견 기록이 같음을 확인했다.
마스크 파일은 검토용 산출물이며 사건 DB에 원본 이미지를 저장한 것은 아니다.

## 코드 검증과 구현 한계

- 관련 회귀 테스트 **302개 통과, 1개 모듈 건너뜀**. 신규 스트리밍 시험은 31개다.
- 미래 시각·중복 시각·관측 간격 초과·대기열 초과를 거절하는지 확인했다.
- 늦은 결과를 성공으로 세거나, 모델에 미래 프레임이 들어간 기록을 정상으로 통과시키지 않는지 검사했다.
- 건너뛴 것은 GPU 전용 Python 환경에 `rclpy`가 없어 수집하지 못한 Manager ROS 통합 시험이다.
  이번 결과에 실제 DDS/Action 통합 통과를 포함하지 않는다.
- 대기열은 최대 64장·16MiB이며 넘치면 오래된 프레임을 조용히 생략하지 않고 시험 세션을 중단한다.
  SAM 세션도 최대 64프레임이다. 무기한 추적, 여러 사람 동시 추적, 자동 세션 교체는 구현하지 않았다.
- SAM의 내부 상태 구조를 사용하는 실험용 어댑터다. upstream commit
  `2b90b9f5ceec907a1c18123530e92e794ad901a4`에 묶여 있고, 운영 노드에서 import하지 않는다.
- GPU 작업과 입력 처리를 분리했지만 프로세스 장애 복구·장시간 메모리·ROS 취소 전달까지 검증한 것은 아니다.

시작 시 코드 해시 수집에서 PyTorch의 가상 모듈 경로를 실제 파일로 취급한 오류가 있어 수정했다.
파일이 실제로 존재하는 로컬 Python 모듈만 기록하도록 했으며 회귀 시험을 추가했다.
집계 스크립트의 중복 키 오류도 수정 후 완료 산출물로 다시 집계했다. 실패 시 원래 데이터를 덮어쓰지 않았다.

## 현재 판단

연속 입력과 GPU 작업을 함께 돌려 사건 처리 코드까지 전달하고, 늦은 결과·중단 후 결과를
거절하는 동작은 확인했다. **실제 Cloud 응답 이후 계속 움직이는 사람을 안정적으로 연결하는지는 미검증**이다.
현재 긴 영상이 없으므로 이 부분을 완료로 표시하거나, 짧은 영상을 반복해 성공률을 만들지 않는다.
연결 순간 미검수 4건과 장시간·교차 장면 검증도 남아 있다. 운영 적용·배포는 하지 않는다.
