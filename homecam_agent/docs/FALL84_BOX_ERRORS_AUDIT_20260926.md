# Gemma·Gemini 좌표 오류 확인

SWM25-186 / 2026-09-26

기존 84개 평가에서 저장한 Gemma·Gemini 응답 168개를 다시 검사했다.
새 API 호출은 하지 않았고, 기존 입력·응답·점수와 운영 코드는 바꾸지 않았다.

이 점검 이후 [평가용 좌표 프롬프트 v3](VLM_BOX_PROMPT_V3_20260926.md)를 별도 추가했다.
아래 내용은 수정 전 응답의 점검 기록이며, 새 프롬프트의 실제 효과를 측정한 결과는 아니다.

## 무엇이 잘못됐나

요청한 좌표는 `[left, top, right, bottom]` 순서의 0~1 값이다.
그런데 저장된 모델 답변에 소수와 수십~수백 단위 숫자가 섞여 있었다.
일부는 네 값 모두 1보다 컸고, 좌우나 위아래가 뒤집힌 답변도 있었다.

아래 건수는 **이미지나 박스 수가 아니라 응답 수**다.

| 응답에서 확인한 문제 | Gemma4 31B | Gemini 3.8 Flash |
|---|---:|---:|
| 한 박스에 0~1 소수와 1보다 큰 숫자가 섞임 | 21건 | 19건 |
| 잘못된 박스의 네 좌표가 모두 1보다 큼 | 4건 | 0건 |
| 좌우 또는 위아래 순서가 뒤집힘 | 1건 | 1건 |
| 오류 응답 합계 | 26/84건 | 20/84건 |
| 오류 응답 중 영상 라벨은 맞힌 수 | 20건 | 18건 |

Gemma의 혼합 오류 21건은 모두 가로 좌표가 0~1 소수이고 세로 좌표가
1보다 큰 형태였다. 해당 응답에 포함된 잘못된 박스는 58개다.
Gemini의 혼합 오류는 49개 박스에서 나왔으며, 세로 좌표뿐 아니라 오른쪽
좌표만 큰 숫자로 나온 경우도 있었다.

뒤집힌 박스까지 포함하면 잘못된 박스는 Gemma 75개, Gemini 50개다.
한 응답에 여러 프레임의 박스가 들어가기 때문에 오류 응답 수와 다르다.

### 실제 답변 예시

| 모델 / 평가 ID | 모델이 반환한 박스 | 문제 |
|---|---|---|
| Gemma / SYN014 | `[0.44, 145, 0.58, 482]` | 가로와 세로 숫자 크기가 다름 |
| Gemma / SYN011 | `[604, 336, 658, 423]` | 네 좌표 모두 0~1 범위 밖 |
| Gemma / SYN079 | `[0.7, 0.32, 0.54, 0.55]` | left가 right보다 큼 |
| Gemini / SYN001 | `[0.441, 246.0, 0.577, 560.0]` | 가로와 세로 숫자 크기가 다름 |
| Gemini / SYN079 | `[0.198, 0.000049, 0.672, 6.42]` | bottom이 범위 밖이며 단순한 정수 출력도 아님 |
| Gemini / SYN083 | `[0.395, 0.82, 0.603, 0.536]` | top이 bottom보다 큼 |

일부 값은 0~1000 좌표처럼 보이지만, 이것만으로 모델이 의도한 좌표계를
확정할 수는 없다. 이미지 크기도 640×400이므로 큰 숫자를 모두 원본 픽셀로
해석할 수 없다. **1000으로 나누거나 좌우를 바꿔서 정답으로 처리하지 않았다.**

## 입력 안내나 검사 코드 문제인가

- 실제 저장된 `explicit_json_v2` 지시문에는 이미 좌표 순서, 0~1 범위,
  픽셀·퍼센트 금지, `left < right`, `top < bottom`, 소수 예시가 들어 있었다.
- Google 응답은 텍스트 부분을 이어 붙이고, Ollama 응답은 `message.content`를
  읽는다. 이 과정에서 좌표의 소수점이나 단위를 변환하는 코드는 없다.
- 검사기는 바깥 코드 블록 한 겹만 제거한다. 숫자를 고치거나 순서를 바꾸지 않는다.
- 이번 요청 코드에는 Gemini의 구조화 출력 스키마 설정이나 Ollama의 `format`
  설정이 없다. 좌표 규칙은 지시문으로 전달하고 응답을 받은 뒤 로컬에서 검사했다.

따라서 확인된 문제는 **모델이 요청한 좌표 규칙을 일관되게 따르지 않은 것**이다.
모델 내부에서 왜 이런 숫자를 생성했는지까지 확인한 것은 아니다.
같은 안내를 한 번 더 적는 것만으로 해결된다고 판단하지 않는다.

## 좌표 오류가 나면 낙상 판단도 없어지는가

운영 코드와 평가 점수는 구분해야 한다.

- 운영 파서는 낙상·낙상 의심 판단은 유지하고 잘못된 위치 정보를 제거한다.
  `localization_failed=True`로 표시한다.
- 모니터는 해당 발견을 `invalid_locations`로 기록한다. 사람이나 사건에
  임의로 연결하지 않으며, 정상 행동으로 바꾸지도 않는다.
- 평가의 ‘라벨 정답 + 응답 검사 통과’ 항목에서는 좌표 오류도 실패이므로
  정답 수에서 제외한다. ‘영상 라벨 정답’에는 원래 답한 라벨을 따로 반영한다.

실제 오류 응답 46개를 운영 파서에 다시 넣어 모두 판단은 유지되고 위치 정보는
사용되지 않는 것을 확인했다. 응답에 올바른 숫자 형태의 박스가 일부 섞여 있어도
현재 코드는 위치 목록 전체를 버린다. 이런 응답은 Gemma 1건, Gemini 9건이었다.
이 동작을 바꾸려면 일부 박스만으로 같은 사람을 연결해도 되는지 별도 검증이 필요하다.

## 다음 수정과 재평가 방향

1. 기존 `explicit_json_v2`와 점수는 그대로 보존하고, 좌표 출력 방식만 바꾼
   별도 평가 조건을 만든다. 영상 판단 기준과 입력 이미지는 유지한다.
2. 현재 0~1 형식을 유지하는 안부터 시험한다. 네 좌표의 축·범위를 각각
   명시하고, 응답 직전 네 값과 순서를 확인하게 한다. 위치를 못 정하면 사람의
   의심 판단은 남기고 `regions: []`를 사용한다. 효과는 재호출로 확인해야 한다.
3. API가 지원하는 구조화 출력·수치 범위 제한을 확인한 뒤 사용 여부를 결정한다.
   범위를 제한하더라도 실제 사람 위치나 좌우·상하 관계까지 맞는 것은 아니다.
4. 혼합 좌표·네 값 모두 범위 밖·뒤집힘·정상 응답을 포함한 소규모 입력으로
   먼저 비교한다. 기존 실패 사례를 고르는 시험은 오류 재현용이지 새 정확도
   점수가 아니다. 비용 한도를 정한 뒤 실제 호출을 시작한다.
5. 형식 오류 수 외에 라벨 정답, 낙상·의심을 정상으로 답한 수, 빈 `regions` 수,
   실제 사람 위치, 응답 시간과 비용을 함께 확인한다. 박스를 전부 비워서
   형식 검사만 통과하는 결과를 개선으로 보지 않는다.

만약 다른 좌표계나 필드 형식이 더 안정적이라면 별도 실험으로 비교할 수 있다.
그 경우에도 요청 단계에서 좌표계를 고정하고 명시적으로 변환해야 하며,
응답 숫자 크기를 보고 좌표계를 추측하는 자동 보정은 추가하지 않는다.

## 확인 범위와 근거

- 평가 시점 소스 파일과 84개 입력 파일의 저장된 SHA-256 일치 확인.
- 두 모델 응답 168개의 라벨·검사 결과·오류 코드 재현. 원본 결과 변경 없음.
- 평가 코드와 사건 연결 관련 기존 테스트 **145개 통과**.
- 이번 작업은 숫자·형식 및 오류 처리 확인이다. 실제 이미지의 정답 박스와
  비교한 위치 정확도나 수정된 프롬프트의 효과는 아직 측정하지 않았다.
- 운영 프롬프트, API 요청 형식, 평가 점수 및 Jira는 변경하지 않았다.
