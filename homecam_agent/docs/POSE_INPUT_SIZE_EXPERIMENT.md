# Pose 입력 크기 비교 — 2026-09-09

## 결론

현재 YOLO26n-pose와 합성 영상에서는 **입력 확대만으로 431번을 해결하지 못했다.**
확인 대상에서 후보가 나오는 영상도 줄어, 기본 입력 640을 유지한다.
실험 모델은 따로 저장했고 운영 모델·검출 기준·추적기·낙상 규칙은 변경하지 않았다.

## 무엇을 비교했나

- 동일한 YOLO26n-pose 가중치를 640×640, 960×960, 1280×1280 고정 입력 ONNX로 내보냄.
  FP32, end-to-end 출력, opset 12, simplify=true. 재학습·다운로드 없음.
- 원본은 세 경우 모두 **640×400, 12fps** 합성 영상이다. 모델 입력에서 확대하는
  실험이며, 더 높은 해상도로 촬영된 원본을 사용한 실험이 아니다.
- 기존 전체 화면 정사각형 변환(stretch)을 유지했다. letterbox·영역 잘라내기·
  모델 크기(n/s/m)·가중치·threshold를 함께 바꾸지 않았다.
- 사람 후보 기준 0.10, 호환용 강한 검출 0.45, 관절 기준 0.5 유지.
- 실제 모델 및 homecam 이미지 콜백을 사용. ROS publisher·일반 검출·depth는
  테스트 대역이다. depth는 없고 로봇 이동은 unknown으로 두었다.
- 같은 41개 영상의 같은 1,106개 표본을 입력 크기별로 실행했다.
  영상별 검수 분류는 결과 집계에만 사용하며 모델·판단 입력에 전달하지 않았다.

## 431번 결과

| 모델 입력 | 최고 검출 점수 | Pose 관측 표본 | 낙상 확인 후보 |
| --- | ---: | ---: | ---: |
| 640×640 | 0.0464 | 0/27 | 0 |
| 960×960 | 0.0942 | 0/27 | 0 |
| 1280×1280 | 0.1141 | 1/27 | 0 |

1280에서는 영상 3.00초에 머리·팔 부근 일부가 약한 사람 후보로 나왔다. 관절 기준을
넘은 출력은 `right_shoulder`, `left_wrist` 두 개뿐이었다. 골반·다리를 포함한 자세를
구성하지 못해 `insufficient_pose`로 남았다. 움직임의 시간 변화도 이어지지 않았다.
박스가 한 번 나왔다는 이유로 낙상을 검출했다고 볼 수 없다.

이 결과는 이번 모델·영상·기준에서 입력 확대가 해결책이 되지 못했다는 뜻이다.
원래 더 높은 해상도로 촬영한 영상이나 다른 모델까지 효과가 없다고 단정하지 않는다.

## 전체 41개 비교

| 모델 입력 | 확인 대상 21개 중 후보 발생 | 정상 활동 20개 중 후보 발생 |
| --- | ---: | ---: |
| 640×640 | 12 | 3 |
| 960×960 | 11 | 2 |
| 1280×1280 | 7 | 1 |

확인 대상은 사람이 검토한 낙상 14개·의심 5개·이미 누운 상태 2개다.
수치는 **영상 단위 후보 발생 수**이며, 대상자·시각별 정답이 없어 낙상 정확도나
정식 recall/FPR/감지 지연으로 보고하지 않는다. 후보 발생은 보호자 알림도 아니다.

- 960: 640에서 잡던 412 후보를 놓쳤고, 새로 후보가 생긴 확인 대상 영상은 없었다.
- 1280: 33 h3·33 ltx·412·414·432 후보를 놓쳤다. 새로 잡은 확인 대상 영상은 없었다.
- 정상 영상 후보는 960에서 108, 1280에서 108·410이 사라졌다. 미탐을 줄이는
  목적에서는 확인 대상 후보까지 함께 줄어든 점을 무시할 수 없다.
- 정상 308에서는 1280 입력에서 두 ID의 확인 후보가 생겼다. 영상 단위로는 1개로
  집계했다. 검출·추적 변동으로 같은 사람에 대한 후보가 나뉠 가능성도 남아 있다.
- 신뢰도나 관절 위치는 입력 크기에 따라 달라졌다. 큰 입력이 같은 검출을 더
  정밀하게 유지한다는 보장은 없으며, 크기를 바꾸면 규칙까지 다시 평가해야 한다.

## PC CPU 처리 시간

Intel Core i5-12400F, ONNX Runtime 1.23.2 CPU, intra-op 2 / inter-op 1,
OpenCV 1스레드. 10회 준비 실행 후 세 크기를 **순차 실행**해 측정했다.

| 모델 입력 | 추론 평균 | 추론 p95 | 콜백 평균 | 콜백 p95 |
| --- | ---: | ---: | ---: | ---: |
| 640×640 | 56.4 ms | 70.5 ms | 60.0 ms | 74.4 ms |
| 960×960 | 128.3 ms | 146.2 ms | 136.7 ms | 157.3 ms |
| 1280×1280 | 238.7 ms | 262.5 ms | 255.0 ms | 279.9 ms |

추론 시간은 `session.run`만, 콜백 시간은 전처리·추론·추적·판단·테스트 발행을 포함한다.
영상 파일 디코딩은 제외했다. p95는 nearest-rank이다. 모델 로딩·준비 실행도 제외했다.
1280 추론은 640 대비 평균 약 4.2배 걸렸다.

오프라인에서 표본을 모두 처리하도록 재생한 결과다. 실제로 5Hz를 유지했다는 뜻이
아니다. 이 PC에서 1280 콜백은 1,106표본 모두 200ms를 넘었다. Jetson·TensorRT·
자율주행·음성과 동시 실행하는 실물 성능은 별도 측정이 필요하다.

## 검증과 결과물

- 세 ONNX 모두 입력 형태 `[1,3,S,S]`, 출력 `[1,300,57]`, 유한값 확인.
- 다시 내보낸 640 모델은 이전 실행의 1,106표본 Pose 관측과 수치가 정확히 일치.
  대상 ID 번호·확인 후보 종류·생성 시각도 일치했다.
- 431·414·412 실제 프레임을 크기별로 비교한 9건에서 PyTorch와 ONNX의
  기준 이상 출력이 허용 오차 안에서 일치. 최대 출력 차이 약 0.0013, 최고 점수
  차이 약 0.000011이다. 전체 영상의 PyTorch 대조를 한 것은 아니다.
- 입력 크기를 키워도 정규화 좌표·검출 기준이 유지되는 계약 테스트 6개 통과.
