# 낙상 감지 지연 측정

2026-09-16. 사용자 요청으로 다음 영상 평가에 감지 지연을 포함한다.
이 문서는 측정 기준이다. 새 영상 생성·시간 라벨 확정·지연 실측은 아직 하지 않았다.
기존 분류 정답과 박스 승인 결과를 바꾸지 않는다.

## 무엇을 잴까?

| 항목 | 시작 | 끝 | 뜻 |
| --- | --- | --- | --- |
| 영상 기준 후보 지연 | 사람이 표시한 동작 시작 | 후보를 만든 입력 프레임 시각 | 몇 초의 영상을 본 뒤 후보가 나왔는지. 추론 처리 시간과 다름 |
| 실제 후보 지연 | 재생 중 동작 시작이 도착한 시각 | 해당 대상의 후보 출력 | 재생·처리·대기를 포함한 YOLO-Pose 경로 지연 |
| VLM 요청 시간 | 요청 전송 시작 | 응답 수신 | 통신·서버 대기·모델 적재·추론 등을 포함한 요청 왕복 시간 |
| 전체 판단 지연 | 재생 중 동작 시작이 도착한 시각 | 해당 대상의 유효한 확인 필요 결과가 준비된 시각 | 후보 생성, 입력 준비, 추가 영상 대기, 요청·응답·검증을 모두 포함 |

VLM이 답변에 적은 사건 발생 시각은 추정값이지 응답 도착 시각이 아니다.
영상의 프레임 시각과 처리 시간을 단순히 더해 실제 전체 지연이라고 표시하지 않는다.
사용자 음성 질문·응답과 보호자 알림 전송은 이번 RGB 모델 평가의 전체 판단 지연에 포함하지 않는다.

## 사람이 표시할 것

- **동작 시작:** 균형이나 지지를 잃고 넘어지는 동작이 처음 보이는 프레임 범위.
  일반적인 걷기 시작이나 정상적으로 몸을 숙이는 시각으로 잡지 않는다.
- **몸 첫 접촉:** 몸통·골반이 바닥이나 낮은 받침에 처음 닿는 범위. 손·무릎 접촉과 구분한다.
  보이지 않으면 모름으로 둔다. 주 지연의 기준은 동작 시작이며, 접촉은 보조 기준이다.
- **이미 바닥에 있는 사람:** 해당 상태를 처음 확인할 수 있는 범위. 낙상 시작은 모름으로 둔다.
  발견 지연을 낙상 시작 지연과 합치지 않는다.
- **애매한 동작:** 분류는 낙상 의심으로 유지한다. 의심 동작의 시작이 보이면 별도 참고 집계한다.
  시작 시각을 표시했다고 낙상이 확정되는 것은 아니다.
- **정상 행동:** 낙상 시작을 만들지 않는다. 불필요한 후보·판정의 발생 시각만 기록한다.

기존 필드 `onset_frames`, `landing_frames`, `first_down_frames`를 재사용한다.
assistant가 해당 구간을 프레임 단위로 확인해 초안을 만들고 사용자가 검토한다.
대표 박스가 있는 1초 간격 프레임에 시작 시각을 억지로 맞추지 않는다.
시작이 애매하면 한 시각으로 단정하지 않고 `[가장 이른 프레임, 가장 늦은 프레임]`을 남긴다.
시각 라벨은 실제 영상·프레임률·해시에 연결하며 프롬프트의 예상 시각을 정답으로 쓰지 않는다.

시작 범위가 `[a, b]`초이고 후보의 영상 시각이 `c`초라면 지연 범위는 `[c-b, c-a]`초다.
고정 프레임률에서는 0부터 세는 `frame / fps`를 사용한다. 다른 프레임률의 영상을 같은 FPS로 계산하지 않는다.
가변 프레임률은 실제 PTS를 확인해야 한다. 음수 지연을 0으로 잘라 감지 성공으로 바꾸지 않는다.
시작 전 후보와 시작 범위에 걸친 후보는 따로 표시하고, 실제 근거 프레임도 확인한다.

## 실제 처리 지연을 재는 실행

- 영상을 1배속으로 도착시키는 재생기가 기준 시계를 가진다. 아직 도착하지 않은 프레임은 모델에 주지 않는다.
- 기준 재생기에서 `replay_start`, `candidate_emitted`, `request_started`, `response_received`,
  `valid_result_ready`를 같은 monotonic 시계로 기록한다. Mac과 Linux의 서로 다른 시계를 직접 빼지 않는다.
- 동작 시작의 실제 기준 범위는 `replay_start + onset_pts`다. 여기서 후보 출력 또는 결과 준비 시각까지 잰다.
- 프레임이 밀리거나 버려지는 경우, 대기열, 영상 입력 구간과 마지막 입력 PTS를 함께 기록한다.
- 첫 모델 적재가 포함된 실행과 적재 후 실행을 구분한다. 장치·모델 digest·입력 크기·프레임 추출 규칙·
  후보 임계값·추가 영상 대기·timeout·재시도 정책을 호출 전에 고정하고 실행 기록에 남긴다.
- 현재 단계에서 새 timeout이나 재시도 횟수는 임의로 정하지 않는다. 실측 전 실행 조건으로 명시한다.

## 세 가지 평가와의 관계

1. **YOLO-Pose 단독:** 올바른 대상의 첫 유효 후보를 기준으로 영상 지연과 실제 후보 지연을 구분한다.
2. **VLM 단독:** 기존 `full`은 전체 영상에서 프레임을 고른 뒤 호출한다. 이 결과의 `request_s`는 요청 시간일 뿐
   실시간 최초 감지 지연이 아니다. 전체 영상 수집 후 판정 지연을 재려면 클립 마지막 프레임이 도착할 때까지의
   대기도 포함해 별도 이름으로 보고한다. 주기적으로 버퍼를 읽는 실시간 VLM 비교는 별도 호출 정책·실행이 필요하다.
3. **YOLO-Pose 후 VLM:** 후보 시점까지 실제 도착한 영상으로 호출하고 최종 결과 시각까지 기록한다.
   기존처럼 후속 영상 대기가 0인지, 추가 관찰 시간을 둘지 실행 전에 고정한다.

정답이 낙상인데 결과가 낙상 의심이면 '확인 필요 포착' 지연에는 포함할 수 있으나,
정확한 3분류 판정의 성공으로 세지는 않는다. 두 결과를 구분해 보고한다.
다른 사람이나 배경에서 나온 빠른 후보를 낙상 대상의 빠른 감지로 세지 않는다.
시간 측정에 필요한 대상 연결이 미확정인 출력은 별도 표시한다.

## 결과에 함께 표시할 것

- 라벨별 전체 영상 수, 대상 포착 수, 영상 내 미검출 수, 잘못된 대상·판정, timeout·오류·미판정 수.
- 낙상 동작 / 의심 동작 / 이미 바닥 상태 발견을 나눈 지연. 서로 다른 시작 기준을 한 평균에 섞지 않는다.
- 지연을 잴 수 있는 성공 사례의 중앙값·p95와 표본 수. 시작이 범위이면 하한·상한을 각각 보고한다.
- 시작 시각을 모르는 사례는 분류·포착률 평가에는 남기고 지연만 모름으로 둔다.
- 미검출이나 실패에 0초 또는 클립 길이를 지연값으로 넣지 않는다. 빠른 성공 사례만으로 전체 성능을 대표하지 않는다.
- 약 5초인 클립에서 신호를 못 찾았으면 '관측 구간 내 미검출'이다. 더 긴 10~20초 대응 능력을 검증한 것으로 쓰지 않는다.

## 현재 가능한 것과 남은 것

- `score_fall_baseline.py::timing`은 시작·최초 발견 프레임 범위 기준의 영상 지연을 이미 계산한다.
- 기존 VLM 실행기는 `request_s`와 일부 모델 처리 시간을 기록한다.
- 기존 41개 시간 검토 이력은 보존하고, 같은 원본에 해당하는지 확인해 재사용한다.
- 추가 36개의 박스는 승인됐지만 시간 라벨은 별도다. 새 생성 영상도 실제 결과를 본 뒤 시간을 표시한다.
- 위 실제 재생 시계·후보 출력·최종 결과 연결은 보강해야 한다. 오프라인 실행 결과만으로 이미 실측했다고 하지 않는다.
- Mac/PC 측정은 해당 실행 환경의 결과다. Jetson에서 음성·주행과 함께 실행하는 제품 지연은 별도 실물 검증이다.
