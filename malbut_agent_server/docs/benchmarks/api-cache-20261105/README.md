# Agent API 계측·캐시 배치 비교 — 2026-11-05

실제 로봇에서 같은 질문으로 24회 호출했다. API 전체 수신 시간은 평균
2.085초 → 1.821초였다. 첫 반복을 제외한 비교는 1.821초 → 1.688초로,
이미 높은 캐시 재사용률에 대한 추가 개선 폭은 작았다. 답변 길이와 추론 토큰도
달라졌으므로 시간 감소분 전부를 캐시 개선의 인과 효과로 해석하지 않는다.

## 비교 조건

- 이전 코드 기준: `bad5fe3289d0a15ddc819d864008e9124bbce97f`.
- 로봇의 실제 OpenAI API, `gpt-5.6-luna`, reasoning `low` 사용.
  모델·출력 한도·기억 검증을 바꾸지 않았다.
- 두 조건 모두 새 계측과 SSE를 사용했다. `baseline`은 기존 입력 배치,
  `cache`는 `MALBUT_AGENT_PROMPT_CACHE_ENABLED=true`인 배치다.
  따라서 이번 비교는 계측 전후의 SSE/JSON 차이를 포함하지 않는다.
- 3문항 × 4회 × 2조건 = 24회. 조건 순서는 AB, BA, AB, BA.
- 각 조건·반복은 같은 운영 SQLite 스냅샷의 별도 복사본에서 시작했다.
  각 복사본 안에서 3문항을 차례로 처리해 앞 답변을 다음 입력에 포함했다.
  첫 문항의 최근 대화 이력은 0턴이었다. 답변이 서로 달라 두 번째 문항부터
  전체 입력이 바이트 단위로 같지는 않다. 긴 대화 이력 시험은 아니다.
- 실제 Agent 오케스트레이터와 최종 기억 검증을 실행했다. 각 응답의
  `memory_validator()`도 확인했다. 24/24 통과, API 시도는 모두 1회였다.
  이 표본의 `long_term_memory.record_count`는 0이므로 다양한 기억 참조의
  정확성을 이 실험만으로 입증하지는 않는다. 정정·삭제 회귀 시험은 별도로 실행했다.
- 비교에서 STT·ROS 전달·TTS는 제외했다. 복사본의 후속 이야기 추출 워커도
  실행하지 않았다. 운영 DB는 비교에 사용한 질문으로 변경하지 않았다.

| 문항 | 동일 입력 |
| --- | --- |
| 1 | 안녕. 짧게 한 문장으로 인사해줘. |
| 2 | 산책이 기분 전환에 도움이 되는 이유를 한 문장으로 말해줘. |

## 운영 Agent 적용 확인

7개 런타임 파일을 백업·해시 검증 후 반영하고 Agent만 재시작했다.
STT·TTS의 PID와 시작 시각은 그대로 유지했다. 새 Agent의 준비 완료를
확인한 뒤 위 3문항을 `/malbut/speech/transcript`로 입력했다.
아래는 실제 Agent → Manager → Piper 재생 시험이며 비교 실험과 섞지 않는다.
STT 시간은 포함하지 않고, 첫 소리는 마이크 측정이 아닌 `playing` 상태 수신 기준이다.

| 적용 후 문항 | API 전체 수신 | 입력 준비 | Agent 전체 | 응답 → 재생 시작 | 입력 → 재생 시작 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 인사 | 2.387초 | 1.012초 | 6.072초 | 0.522초 | 6.594초 |
| 산책 | 2.137초 | 0.109초 | 3.262초 | 1.938초 | 5.200초 |
| 계획 변경 | 1.882초 | 0.135초 | 5.290초 | 1.659초 | 6.949초 |

3/3 최종 응답이 한 번씩 발행되고 재생 완료됐다. 발행 시점에는 저장이
`pending`이었고, 이후 모두 `completed`와 새 API 계측값 저장을 확인했다.
남은 pending 턴은 0개였다. 후속 기억 추출도 운영 설정대로 실행됐다.

실제 대화 전체의 기다림은 API 수치보다 길다. 특히 재시작 직후 첫 입력 준비
1.012초와 API 밖의 Agent 처리·재생 준비가 남았다. 이번 계측은 입력 준비
내부 작업이나 API 밖 처리의 세부 원인까지 나누지는 않는다. 이를 별도 측정하기
전까지 토큰 계산·DB·백그라운드 작업 중 하나로 단정하지 않는다.
