### 요약 대상과 최근 원문의 경계 수정

위 선물안 사례의 오류는 요약 API가 압축 대상뿐 아니라 최근 원문도 참고로
받으면서 생겼다. 최신 구현은 **직전 요약과 압축할 원문 앞부분만** 요약기에
보내고 prompt revision을 4로 기록한다. 최근 원문의 분할·예산 계산은 유지하며,
최근 정정과 현재 요청은 기존대로 답변 모델에 별도로 전달한다. 요약에 포함할
수 없는 자료를 API 입력에서 제외하므로 중복 입력 비용도 줄어든다.

[같은 세 입력의 재검사](conversation-summary-source-prefix-2026-09-24.json)는
저가 요약 3회와 선물안 후속 답변 1회, 총 4회만 호출했다. 세 요약의 source는
이전 평가와 같고, 최근 원문·현재 probe·기대 사실은 요약 요청에 없음을 검사했다.
이번 출력에서는 최근 원문만의 새 사실이나 요청 편입을 발견하지 못했으며,
선물안 답변도 최근 요청에 맞춰 첫 장소 문구 한 줄을 제시했다. 다만 요약이
첫째 엽서·둘째 지도·셋째 음성이라는 후보 번호 대응을 생략했다. 최근 원문이
둘째=지도 연결을 보완해 해당 답변은 맞았지만 요약 자체의 완전 보존은 아니다.

요약 3회의 API 입력은 **5,857→5,010토큰(14.46% 감소)**이다. 출력·캐시를
포함한 추정 비용은 **$0.0016369→$0.001295025(20.89% 감소)**였으나, 사례별
1회 출력과 변경된 지시를 함께 비교한 값이므로 일반적인 절감률로 보장하지 않는다.
새 통합 회귀는 실제 요약 adapter의 전송 입력과 압축 후 provider 이력,
SQLite 전체 원문의 내용·순서를 함께 확인한다. 기존 요약 실패·재시작·비동기
대화 진행 검사는 그대로 통과했다. 앞선 최종 답변 조건 누락은 별도 미해결이다.

### 저가 대화 모델의 조건 보존 대조

[저가 대화 모델 비교](conversation-foreground-luna6-comparison-2026-09-24.json)는
기존 실패 사례 세 payload의 `model`만 `gpt-6-luna`로 바꿔 3회 호출했다.
초대문은 인원·무료·교환 의무 없음, 소풍 문자는 재료·오이 제외 누락을 유지했다.
일정은 버스 한 구간을 25분 이내로 바꿔 해당 위반이 개선됐다. 그러나 이 응답은
진단용 30초 제한에서 6.337초가 걸렸으므로 운영 기본 5초 시도의 통과 근거가
아니다. 초대문 입력은 이전 모델 대조에 보관한 당시 payload이며 현재 prompt와
완전히 같지는 않다. **전경 기본값은 바꾸지 않았고**, 모델 교체로 조건 누락이
해결됐다고 판단하지 않는다. 요약 기본값은 계속 `gpt-6-luna / low`다.

### 후보 순서 참조의 원문 복원

요약에서 빠진 후보 번호를 다시 물을 때 기존 조회가 “처음에”는 인식하지만
“처음 제안한 것”, “두번째안”은 인식하지 않는 결함을
[오프라인 전후 판정](conversation-recall-ordinal-2026-09-24.json)으로 확인했다.
이런 과거 제안·순서 참조도 기존 원문 조회로 연결하고, 검색할 때만
“두 번째/2번째/둘째” 표기를 같은 순서 단위로 정규화한다. 관련 순서를 포함한
원문을 우선하며 숫자 2를 12의 일부로 매칭하지 않는다. 반복 횟수나 버튼·
안전장치 실행 표현은 이 새 참조 조건으로 활성화하지 않는다.

작은 토큰 예산에서 요약에 빠진 후보 순서 원문을 복원하고, 최근 원문 순서와
저장된 요약을 유지하는 회귀를 추가했다. 동일 사용자·세션·instance·generation,
삭제·동의 필터, 기존 2,048토큰 예산과 완결 턴 선택은 유지했다. 추가 모델 호출,
새 저장소나 사례의 정답 단어는 넣지 않았다. 이는 근거를 답변 입력에 복원하는
수정이며, 임의의 지시 대상 해석이나 최종 답변의 의미 준수를 보장하지 않는다.

### 요청한 문장을 삭제하던 듣기 후처리 제거

듣기 모드에서 이전 답변이 “편하게 말씀해 주세요.”일 때 사용자가 이 문장을
그대로 다시 써 달라고 하면, 모델이 정확한 문장을 생성해도 정규식 후처리가
본문을 지워 “네.”로 전달·저장하는 결함을 재현했다. 직전 문장 재출력, 번역,
여러 문장과 줄바꿈 보존 요청에도 같은 삭제가 발생했다. 이는 알려진 모델의
조건 누락과 별개인 adapter의 내용 소실이다.

자연어 요청별 예외를 늘리지 않고 `OpenAIResponsesProvider`의 해당 삭제 분기와
helper를 제거했다. 공통 prompt와 듣기 모드 schema의 반복 억제 지시는 유지한다.
현재 요청의 산출물이 안내 문형과 같을 수 있으므로 문자열 모양만으로 삭제하지
않는다. 그 대신 모델이 반복 문구를 생성하면 이제 그대로 전달될 수 있으며,
반복 억제 품질을 프로그램으로 보장하지 않는다.

`test_semantic_prompting.py`의 새 4개 사례는 실제 orchestrator·설정 저장·provider·
SQLite commit을 사용하고 네트워크 응답만 통제한다. 수정 전 네 사례 모두
내용 삭제로 실패했고, 수정 후 전달·저장된 본문과 줄바꿈이 일치했다. 기존
내용 보존 6개 사례도 helper 직접 검사에서 실제 provider 경로로 옮겼다.
삭제 동작을 요구하던 helper 전용 검사는 제거했으며 관련 파일은 **22 passed**다.
이 수정에 새 유료 호출·모델 변경·장치 동작은 없다.

[OpenAI 응답 길이 지침](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.6)을
따른다. 다른 모델이나 기억 추출 전용 호출에는 이 필드를 추가하지 않는다.

중간 구현의 350자 schema 강제 제한은 문장 중간에서 끝나는 출력을 만들었고,
사후 문장 분할은 뒤쪽 필수 조건을 누락시킬 수 있어 모두 제거했다.
완성 응답의 뒤쪽 안전 조건과 듣기 문구에 결합된 새 사실을 그대로 보존하는
회귀 검사를 추가했다. 이전 `bounded/segmented/listen-delivery` 파일은 이
과정을 보여 주는 과거 산출물이며 현재 구현의 검증 결과가 아니다.

설명 부분만의 길이, 실제 청취 내용은 검사하지 않았다. 첫 PCM 반환 대기는
초기 400ms 분량 버퍼가 준비된 시간이며 원시 첫 바이트나 스피커 시작 시간이
아니다. 두 표본은 약 30초 분량의 근거이지만 문자 수에 따른 모든 응답의
30초 상한, 실제 재생 완료 `finished`, Jetson 음성 왕복 지연을 보장하지 않는다.
바이너리 응답에 토큰 사용량이 없어 호출 비용이나 청구액을 시간에서 역산하지 않았다.

## 남아 있는 검증과 한계

### 운영 예산·반복 압축 추가 검증

[실행기](../../tools/conversation_context_smoke.py)는 합성 원문을 실제
orchestrator/SQLite에 넣고, 운영 기본 예산 **16,384토큰**에서 두 차례
백그라운드 압축을 유발한다. 삽입한 원문의 응답은 fixture이고, 요약과
6개 후속 응답만 실제 모델이 생성한다. 따라서 실제 사용자가 129턴을
자연스럽게 대화한 기록이나 음성 실기 결과가 아니다. 비교적 관련성이 낮은
읽기 예문을 넣은 검사이며, 모든 턴에 중요한 조건이 밀집한 부하를 대표하지 않는다.

[최종 원문·입력·응답](conversation-context-default-final-2026-09-24.json)의 결과:

| 항목 | 첫 압축 | 두 번째 압축 |
|---|---:|---:|
| 압축 시작 전 대화 추정 토큰 | 14,949 | 14,820 |
| 적용 후 대화 추정 토큰 | 2,934 | 2,780 |
| 요약 API 시간 | 10.442초 | 7.969초 |
| 동시에 진행한 전경 답변 API 시간 | 3.725초 | 2.568초 |

두 전경 답변은 요약보다 먼저 완료했다. 두 번째 압축 시작 시점에는 없는
오후 3시 정정을 최근 원문으로 보존하고 다음 답변에 반영했다. 재시작 시
세션 ID·요약·원문 128턴의 내용과 순서가 같았으며, 마지막 답변 뒤 총
129턴을 보관했다. 사용자/친구의 취미, 귤 담당, 미정인 발표 순서와 폐기한
이름 후보도 구분했다. 초기 검사에서 snapshot 기본 조회 한도 100개를
전체 원문 수로 오인하지 않도록 실행기를 고쳤고, 최종 검사는 삽입·생성한
전체 턴 수와 실제 조회 수를 함께 확인했다.

**이 검사에서 최종 초대문의 전체 조건 보존은 미충족이다.** 요약에는 인원·무료
참여·물건 교환 의무 없음이 남아 있지만 최종 본문에는 이 조건들이 빠졌다.
모델이 이전 초안의 누락을 이어받는 현상을 확인해 사용자 요구와 초안을
구분하는 지시를 보완하고 요약 prompt revision을 3으로 올렸으나, 이 표본에서
누락은 해결되지 않았다. 응답 앞에 필수 조건 목록을 생성시키는 추가 필드도
실험했지만 충분한 개선을 입증하지 못해 **현재 runtime에서는 제거했다**.
`default-v3`와 `conditions-probe`는 그 중간 실험이며 현재 응답 계약이 아니다.

### 조건 누락 원인 분리

동일한 합성 입력을 사용한 추가 진단 **15회 호출(답변 14회, 요약 1회)**을
완료했다. 각 파일은 실험별 요청 payload와 API 응답을 보관하며, 아래의
변경은 효과가 확인되지 않아 운영 코드에 적용하지 않았다.

| 비교 | 관찰 결과 |
|---|---|
| [기존 순서와 요약→최근 원문→현재 요청 순서](conversation-context-cause-probe-2026-09-24.json) | 두 후속 질문 모두 조건 누락 지속 |
| [요약 호출 reasoning=low](conversation-context-cause-probe-2026-09-24.json) | 불완전한 작성안은 줄었으나 후속 답변은 조건 누락 지속, 한 응답은 3문장 요구를 4문장으로 위반 |
| [API의 user/assistant 메시지 구분](conversation-context-native-roles-2026-09-24.json) | 두 후속 질문 모두 조건 누락 지속 |
| [실제 원문 중 해당 작업의 사용자 발화 전체 추가](conversation-context-native-roles-2026-09-24.json) | 같은 결과. 평가용 기대 답변이나 required_facts는 입력하지 않음. 관련 원문 전체를 수동 선택한 진단이며 운영 검색 성능 근거는 아님 |
| [verbosity=medium 및 응답 schema 설명의 길이 지시 제거](conversation-context-verbosity-probe-2026-09-24.json) | 네 응답 모두 조건 누락 지속 |

기존 최종 응답은 앞선 불완전한 초안에서 시작 시간만 2시→3시로 바꾼
문자열과 같았다. 그 입력에는 인원·참가비·교환 의무 조건이 모두 있었으며
원문과 요약의 잘림 표시도 없었다. 이후 추가 진단 **8회**에서는 다음도 확인했다.

- [초안·요약을 제외하고 해당 작업의 사용자 원문만 제공](conversation-context-coverage-probe-2026-09-24.json):
  두 응답 모두 조건 누락이 남았다. 같은 파일의 명시적인 본문 조건 포함 지시도
  두 응답 모두 해결하지 못했다. 수동으로 관련 원문을 고른 원인 분리 실험이며
  현재 운영 컨텍스트를 이렇게 잘라 구성하지 않는다.
- [답변 reasoning=high](conversation-context-high-probe-2026-09-24.json):
  다른 입력과 출력 상한은 유지했고 두 응답 모두 조건 누락이 남았다.
- [생성 초안을 독립된 두 번째 호출로 검토·수정](conversation-context-review-probe-2026-09-24.json):
  빠진 조건을 개별적으로 알려주지 않고 원래 입력과 초안을 제공했으나 두 응답
  모두 같은 누락을 유지했다. 추가 검토 호출은 운영 경로에 넣지 않았다.

따라서 **저장된 사실의 소실과 실제 답변의 조건 누락은 구분해야 한다.** 초안
복제 현상은 확인됐으나 초안이 없는 입력도 실패하여 단독 원인으로 확정하지
않는다. 메시지 순서·역할·원문 추가·추론 강화·출력 길이·자체 검토만으로
해결됐다는 근거도 없다. 실패한 실험을 운영 변경이나 품질 개선으로 집계하지 않는다.

누락 판정은 모든 배경 사실을 초대문에 나열하라는 뜻이 아니다. 원문에서
사용자는 정한 내용을 초대문으로 정리하려는 목적을 밝히고, 물건 교환 의무가
없다는 참여 조건과 사용자 포함 다섯 명이라는 범위를 재확인했다. 따라서 인원·
무료·교환 의무 없음은 이 산출물에 필요한 조건이다. 반면 폐기한 이름·옛 장소·
말투 변경 이력은 나열할 필요가 없고, 주소·개인 음료 취향·농담은 제외해야 한다.
세 문장이라는 형식 안에 위 조건을 함께 담을 수 있어 조건 충돌로 처리하지 않는다.

### 초기값 보존 요청 회귀

“기본 설정은 바꾸지 말고 이번 답변만 반말로 해줘”가 문두의 “기본 설정”
때문에 저장 요청으로 분류되던 오류를 수정했다. 기본값 유지 요청 뒤에 있는
현재 답변/세션 변경은 지정된 범위에만 적용하며, 저장된 초기값은 유지한다.
실제 턴 커밋을 거쳐 현재 답변·다음 답변·새 세션의 설정을 확인했다.
구조화된 `호칭=유지하`의 값은 유지 명령으로 해석하지 않는다.

“기본 설정 화면에는 반말로 해달라는 문구가 있어” 같은 보고를 저장 명령으로
오인하던 문제도 고쳤다. 인용·보고·부정은 설정을 바꾸지 않고 직접 변경 요청은
유지한다. “수민이에게 반말로 말해줘”는 그 수신자를 위한 현재 답변에만 적용하며
사용자에게 답하는 세션 말투로 저장하지 않는다. “앞으로/항상”이 있어도 다른
수신자의 말투를 사용자 기본값으로 확대하지 않는다. 반면 “나에게/저한테”는
세션 설정으로 처리한다. 현재 답변·다음 답변·저장값을 함께 검증했다.

### 조건 검사기의 독립 평가

답변 작성과 분리한 [검사 실행기](../../tools/conversation_constraint_audit.py)로
원문·현재 요청·후보 답변만 제공하고 조건별 충족 여부를 검사했다. 기대 판정은
`evaluation_only`에 따로 저장하며 모델 입력에 넣지 않는다. 실행당 최대 8회
호출을 허용하고 API 키·요청 헤더·예외 본문은 결과에 저장하지 않는다.

[기존 실패와 정상·오류 대조군](conversation-constraint-audit-2026-09-24.json),
[별도 두 주제의 대조군](conversation-constraint-audit-heldout-2026-09-24.json)을
합친 **7개 후보의 의미 판정은 4개 통과**였다. 정상 세 후보에는 오류를 잘못
붙이지 않았고, 준비 담당을 뒤집은 후보는 검출했다. 그러나 원래 초대문의
세 누락은 모두 놓쳤으며, 책 모임의 예약금 없음도 놓쳤다. 보리차를 본문에서
빼라는 지시 위반을 찾으면서 이미 알려진 보리차를 새 준비물이라고 추가 지적한
오탐도 있었다. 누락을 일부 찾았다는 이유로 그 후보 전체를 통과시키지 않았다.

정확한 인용 여부는 별도 검사했다. 7개 결과에서 원문 인용 5개와 후보 인용
10개가 실제 입력의 연속 구절과 일치하지 않았다. 일부는 생략 부호·여러 구절의
재구성이며, 일부는 “주소 언급 없음” 같은 판정 설명이었다. 실행기에 이 대조를
추가하고, 정답 입력 분리·호출 상한·인용 불일치 기록을 로컬 회귀 검사로 남겼다.
정확한 인용 계약까지 포함하면 7개 중 1개만 모든 평가 조건을 충족한다.

[부정형 사실과 언급 금지를 구분하는 추가 지시](conversation-constraint-audit-negative-2026-09-24.json)도
두 실패 후보를 해결하지 못했다. 따라서 **이 검사기를 운영 응답의 자동 보정이나
통과 판정에 연결하지 않았다.** 평가 도구의 추가는 생성 품질 개선으로 집계하지 않는다.

### 모델만 바꾼 비교와 실제 Astra 운영 경로

기존 두 최종 작성 요청의 저장된 payload를 재생해 `model`만 바꿨다.
입력·지시·reasoning·출력 상한·`verbosity=low`는 같으며, 새 발신자 관점
지시는 이 비교에 추가하지 않았다. [Sol 두 응답](conversation-context-sol-contrast-2026-09-24.json)은
세 조건 누락이 남았지만, [Astra 두 응답](conversation-context-astra-contrast-2026-09-24.json)은
사용자 포함 5명·참가비 없음·물건 교환 의무 없음을 모두 본문에 포함했다.
사용자 발신자 시점, 시간 정정, 본문 세 문장·반말도 지켰다. 응답 시간은
Astra 5.837/9.232초, Sol 3.823/4.079초였다. 입력별 모델당 한 번이며 캐시와
서버 상태를 통제한 반복 속도 실험이 아니므로 성능 우열로 일반화하지 않는다.

실제 운영 경로에서는 별도 문제가 드러났다. 요약기가 `reasoning.effort=none`을
고정해 [첫 Astra 실행](conversation-context-astra-production-2026-09-24.json)의
요약 요청이 HTTP 400으로 거절됐다. 작은 합성 요청으로 오류의 제한된 메타데이터만
확인했고, `code=unsupported_value`, `param=reasoning.effort`였다. 기존
`OPENAI_REASONING_EFFORT`를 요약기에도 전달하고 저장된 요약의 `state_json`에
실제 값을 남기도록 수정했다. 지원 값 검증에는 기존 공통 허용 목록을 재사용한다.

수정 뒤 [30초 제한 실행](conversation-context-astra-production-fixed-2026-09-24.json)은
해당 HTTP 오류 대신 30.14초에 요약 시간 초과로 끝났다. 요약 제한은 기존
30초를 유지하되 요청 시간 설정이 더 길면 `max(30, request_timeout_seconds)`로
반영한다. 전경 요청의 기본 5초를 요약에도 그대로 적용하는 회귀는 방지했다.
평가 실행기도 기존 두 시간 설정을 읽고 실제 API의 reasoning·제한 시간·출력
상한을 기록한다. 이 호환성 수정 단계에서는 새 환경변수나 모델별 특수 분기를
추가하지 않았고, 이후 비용 요청으로 위의 요약 전용 설정 두 개를 분리했다.

[Astra 120초 프로필](conversation-context-astra-120s-2026-09-24.json)은 현재
운영 코드를 그대로 사용해 두 압축과 재시작까지 완료했다. 평가에만
`OPENAI_MODEL=gpt-6-astra`, 요청 120초, 전체 요청 예산 241초를 명시했다.
기본 모델·기본 시간 설정은 바꾸지 않았다.

| 단계 | 압축 전→후 추정 토큰 | 요약 소요 | 동시 전경 답변 소요 |
|---|---:|---:|---:|
| 첫 압축 | 14,759→4,880 | 57.403초 | 4.750초 |
| 두 번째 압축 | 14,788→5,103 | 55.227초 | 5.041초 |

113개 fixture 턴과 6개 실제 응답, 요약 2회를 사용했다. 재시작 시 같은 세션·
최신 요약·118개 원문의 순서와 내용을 확인했고 마지막 질의 뒤에는 119개
원문이 남았다. 두 최종 초대문은 앞서 누락된 세 조건을 포함하고, 두 번째는
압축 중 정정한 15시 시작을 반영했다. 원문 인용과 재시작 후 취미의 주체·귤
준비 담당·미정 소개 순서도 확인했다. 두 번째 압축 후 분량은 30% 목표를

### 재설명·유머·개인 취향 추가 검증

기본 응답 reasoning을 `none`에서 **`low`**로 변경했다. 아래 초기 품질 검사
시점의 요약 호출은 `none`이었으며, 이후 모델 호환성 수정으로 요약에도
설정된 reasoning 값을 전달한다. 현재는 위의 요약 전용 설정을 사용한다.
명시적인 환경 설정은 새 기본값보다
우선한다. 문장 지시만으로 해결되지 않던 반복된 이해 어려움의
확인 질문이 `low` 표본에서 개선됐다. 평균 약 1.2초의 추가 지연을 관찰했으나,
prompt의 글 작성 규칙도 달라 순수한 reasoning 단독 A/B로 해석하지 않는다.

[최종 품질 검사](conversation-quality-final-2026-09-24.json)는 3사례·8턴,
8개 API 응답이 모두 완료됐다. 처음 이해가 어렵다고 하면 쉬운 예시로
재설명하고, 다시 어렵다고 하면 구체적인 혼란 지점을 묻는 순서를 지켰다.
불편한 농담은 멈췄으며, 차 선호에 말하지 않은 온도·종류·습관을 덧붙이지
않았다. [실행기](../../tools/conversation_quality_smoke.py)는 실제 호출을
재시도 포함 10회로 제한한다. 이는 해당 표본의 통과이며 일반적 준수율이 아니다.

[low 기본값의 기존 14사례 재검사](conversation-spec-low-final-2026-09-24.json)도
24턴을 완료했다. 정정, 주제 복귀, 일회 말투, 지역 거부, 세 문장 공지의
조건 보존은 확인했다. 다만 듣기 선언의 새로운 변형이 반복되고, 요청하지
않은 제목이 초기 공지에 붙는 경우가 남았다. 최종 초대문에서는 제목 없이
세 문장과 지정된 조건을 지켰다. 문장 길이나 표현 억제 전체가 보장된다는
근거로 사용하지 않는다.

### 모호함·필수 정보·거부·확정 구분 추가 검증

| 사례 | 확인한 결과 |
|---|---|

발신자 관점에는 공통 대화 지시 세 줄을 추가했다. 사용자 대신 보낼 글은
기본적으로 사용자를 발신자로 삼고, 명시적으로 다른 발신자나 제삼자 서술을
요청하면 그 관점을 우선한다. 응답 문자열을 사후 치환하지 않는다.

다만 미나 사례의 최초 자발적 초안에서는 자기 이름을 삼인칭으로 쓰는 표현이
남았다. 지정된 최종 작성 요청의 표본 통과이며 모든 발신자 관점의 보장은 아니다.

### 겹치는 재시작 복구와 추가 한정 감사

겹치는 재시작 경계도 추가로 확인했다. 새 런타임 B가 pending 없는 상태에서
시작한 뒤 기존 프로세스 A가 새 턴을 예약하고 죽으면, B는 시작 시점의 복구
목록에 해당 세션이 없어 후속 요청마다 충돌하던 결함이 있었다. 파일 DB에서는
매 요청의 세션 OS 잠금을 확보한 뒤 기존 중단 턴 복구 함수를 적용하도록
조건 하나를 변경했다. 현재 살아 있는 요청은 잠금으로 보호하고, 실제 OS 잠금이
없는 `:memory:`는 자동 복구에서 제외하여 자기 pending을 지우지 않는다.

`test_conversation_ownership.py`는 실제 자식 프로세스의 시작·대기·요청 예약·
강제 종료 순서를 제어해 두 재시작 순서를 모두 검증한다. 새 경합 사례는 수정 전
실패했고, 수정 후 기존 live-owner 보호와 파일/메모리 재진입 보호까지 통과했다.
세션 시각·임시 말투·완료 원문·턴 ID는 유지되고 고아 pending만 제거된다.
관련 5개 파일 103개 회귀를 통과했으며 API나 물리 장치는 호출하지 않았다.

추가 한정 감사에서는 응답 설정의 기본/세션/한 답변 범위와 기억 동의 분리,
요청별 재시도·지연 안내·위치 저장 재전송 금지에서 새 확정 결함을 찾지 못했다.
§7 관련 12개 오프라인 회귀도 통과했다. 일반 자연어 이해나 실제 음성 동작의
완전성을 증명한 감사로 확대하지 않는다.

### 계속 필요한 검증

1. 두 저장 응답의 실제 TTS 음원은 25.55/27.90초로 확인했다. 실제
   microphone→STT→Agent→TTS 재생, Jetson 부하 중 지연과 다양한 답변의
   길이는 아직 실기 검증하지 않았다. 문자 기준을 재생 초 단위의 보장으로
   해석하지 않는다.
2. 자연어 이해·공감·정정·유머·조건 보존은 유한한 합성 사례 검증이다.
   이를 모든 자유 대화의 명세 충족이나 장시간 품질 보장으로 표시하지 않는다.
   초심자 설명의 미설명 전문용어, 반복 안내 변형, 장문 이후의 조건 누락 등
   규칙·어휘·출력 형식의 일반화된 품질 보장은 남은 과제다.
3. 원문 재조회는 단어 기반이므로 의미는 같지만 표현이 다른 질의에는 관련
   원문 선택을 놓칠 수 있다. 정확한 문구를 확인하지 못하면 만들지 않도록 지시한다.
4. 1시간 자동 선택과 명시적 새 시작은 음성 워커에 연결했다. HTTP의 명시적
   conversation ID 및 reset API 계약을 임의로 변경하지 않았다.
5. Mock/RAI의 이전 컨텍스트/시도 정책은 별도 경로로 남는다. 운영 예산에서
   두 번의 압축은 확인했으나 실제 장시간 대화와 중요한 사실이 밀집한
   기록에서의 누적 의미 보존은 추가 평가가 필요하다.

따라서 현재 결과는 **OpenAI 운영 경로의 구현과 로컬 검증**이다. 물리 음성
환경과 모든 의미 품질까지 포함한 명세 전체 완료로 판정하지 않는다.
