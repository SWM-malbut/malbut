# SWM25-75~77 강화 후 기능별 300회 오프라인 반복 검증

## 결론

2026-08-13 최종 소스에서 SWM25-75, SWM25-76, SWM25-77의 대표
오프라인 계약을 story별 300회 다시 실행했다. 결과는 **900/900 story
iteration**, **40,500/40,500 subcheck**, 실패 0건이다.

이 수치는 합성 입력, package 내부 임시 SQLite, MockProvider와
Noop/Recording renderer를 사용한 결정론적 회귀 증거다. 실제 사용자·음성·화면
출력 300회, 실제 ROS 실행 또는 운영 성능 SLA를 뜻하지 않는다.

first-open·writer 경합 검사를 포함한 단일 iteration의 로컬 관측값이다. 이
시간값은 benchmark나 배포 latency gate로 사용하지 않는다.

원본 machine-readable 증거는 runner가 생성한 시점에 mode `0600`인
[`SWM25-75_77_300X_OFFLINE_2026-08-13.json`](artifacts/SWM25-75_77_300X_OFFLINE_2026-08-13.json)에

## 기능별 반복 검증 범위

### SWM25-75 — 35개 × 300회

- 사용자별 검색·조회·변경·audit 격리와 정확한 만료 경계
- 확인 기반 create/update/delete, record CAS, user/global revision
- 재시작·두 connection 뒤 create/update/delete durable replay
- v1/v2 schema의 v3 migration, 동시 first-open, 실패 rollback
- unmanaged·legacy memory row DML writer gate와 공유 conversation DB 공존
- 같은 사용자의 current-generation completed turn만 evidence로 인정
- pending·다른 사용자·closed·expired evidence의 신규 변경 차단
- reset generation 및 delete/recreate session instance provenance 구분
- `session_instance_id`, generation, completed time의 row·audit·idempotency 결속
- low-level 호환 경로의 명시적 unknown provenance
- 두 service connection의 동일 요청 1 commit·1 replay
- 두 service connection의 다른 payload 1 commit·1 conflict
- audit/idempotency table에 기억 본문 비복제
- 실제 v2 table·legacy row의 v3 migration과 provenance column 불일치 차단
- provider가 전달받은 memory copy를 변조해도 서버 snapshot fence 유지
- 추론 중 memory 변경·만료와 conversation reset의 늦은 응답 폐기
- 독립 conversation의 provider 호출이 대화별 lock에서 병렬 진행

501개 완료 turn 뒤 exact evidence 조회는 약 1초가 필요한 경계 시험이라 전체
suite에서 1회 확인했으며 이 300회 matrix에는 넣지 않았다.

### SWM25-76 — 45개 × 300회

- raw audio·PCM·path·URI와 transcript `user_id` strict 거절
- partial·저신뢰·binding mismatch·self-echo·stale에서 provider 0회
- final transcript만 Agent에 전달하고 최종 Safety 문구만 TTS 예약
- 빈·공백 Agent 메시지를 durable commit 전에 거절
- duplicate at-most-once, payload conflict와 capture epoch fence
- provider 중 barge-in·close의 비차단 처리와 늦은 응답 폐기
- result-aware completion guard 안의 DB commit·responded/TTS 예약 선형화
- 한 session의 느린 commit이 다른 session barge-in을 막지 않음
- 외부 conversation close·expire·delete의 typed fail-closed 처리
- provider 실패·일시적 conflict 뒤 in-flight 예약 복구
- session close·TTS terminal·evicted activity replay의 늦은 효과 차단
- cancellation fallback, barge-in 뒤 provider 실패와 supersession·DB 오류 경합
- audit projection의 transcript·speaker·audio 본문 비저장

### SWM25-77 — 55개 × 300회

- 5종 emotion, visual-only, intensity·duration·TTL strict schema
- 본문·사용자·반려동물 심리 상태를 읽지 않는 로컬 mapper
- emergency > privacy > availability > freshness 우선순위
- trusted-state revision으로 submit 예약 경쟁 중 긴급 상태 유실 차단
- exact dispatch TTL, display expiry와 neutral 단회 복귀
- 순차·동시 duplicate, payload conflict와 rate limit
- renderer worker 시작 실패 뒤 pending lane 해제·결과 replay
- block renderer 중 긴급 neutral 비차단 처리
- 늦은 renderer 결과의 generation/cancel fence
- receiver generation fence와 explicit neutral supersession
- renderer 오류의 neutral 1회 fallback 및 실패 뒤 disable
- control lane busy, pending payload conflict, 긴급 중 fallback·worker-start 취소
- `express_emotion` 모델 Tool·motion·audio 권한 부재

의도적으로 기다리는 실제 30ms timeout 시험은 전체 suite에서 1회 확인했다.
300회 matrix에는 같은 안전 경계를 더 빠르게 반복하는 Event 기반 generation
경쟁 시험을 넣었다.

## 강화 과정에서 수정한 주요 결함

초기 오프라인 MVP 이후 별도 적대 검토로 다음 문제를 재현하고 수정했다.

1. memory migration 동시 first-open의 duplicate ALTER·writer lock 잔류
2. provider가 전달받은 memory list를 바꿔 snapshot fence를 우회하는 문제
3. memory exact retry가 시간 만료 뒤 실패하거나 만료 row를 되살리는 문제
4. 검증된 evidence의 session instance·generation provenance 유실
5. 거절된 높은 speech sequence와 evicted activity replay가 다음 발화를 막는 문제
6. 느린 provider 중 barge-in·close가 전역 lock에 막히는 문제
7. DB assistant turn과 로컬 TTS 예약 사이의 경쟁 및 빈 TTS 메시지
8. expression conflict·미래 cue·출처 가장·neutral 반복 오류
9. block renderer, worker 시작 실패, 늦은 success와 긴급 lost-update race
10. 영문 후행 수식어가 붙은 명시적 이동 금지문 승인 우회
11. 긴급 neutral timeout 뒤 renderer가 다시 활성화될 수 있던 문제
12. Gateway executor의 무제한 대기열과 boolean 정수 설정 허용

이번 artifact는 위 수정 뒤 전체 matrix를 처음부터 다시 실행한 결과다. artifact
생성 당시 소스는 로컬 전용 브랜치의 미커밋 변경을 포함했으므로 `git_head`만으로
식별하지 않고 runner, 실제 선택 test 5개, production Python 전체를 합친 **30개 파일의
실제 byte SHA-256**을 기록했다. runner는 시작과 종료 manifest가 다르면
artifact를 만들지 않고 실패한다. 최종 artifact의
`source_unchanged_during_run`은 `true`이며 종료 직후 30/30 해시 일치를 다시
확인했다.

## 이 결과로 닫히지 않는 blocker

### SWM25-75

- evidence read와 memory mutation이 별도 transaction인 cross-process TOCTOU
- memory snapshot 재검사와 conversation response commit 사이 TOCTOU
- 신뢰된 person identity와 1회성 confirmation-token CAS
- 인증된 public HTTP/ROS adapter, 보존 기간과 파생 대화 삭제 정책
- SQLite DML trigger를 넘어선 DDL·파일 변조 방어

### SWM25-76

- 실제 STT/TTS/ROS, 한국어 WER, 음향 echo와 latency
- 실제 TTS dispatcher의 durable outbox와 publish/cancel ordering
- coordinator 인스턴스 밖의 durable speech-session lease
- 재시작 안전한 speech/TTS ledger와 provider cooperative cancellation

### SWM25-77

- 실제 frontend·ROS renderer와 receiver-side generation 원자 fence 검증
- 취소를 무시하는 Python renderer thread의 강제 종료·프로세스 격리
- 재시작 뒤 exactly-once를 위한 durable renderer ledger
- 실제 안전 상태 revision 공급자와 제품 intensity·rate·접근성 승인값

## 재현 명령

```bash
cd ~/ros2_ws/src/malbut/malbut_agent_server

PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=. \
python3 scripts/run_swm25_75_77_stress.py \
  --iterations 300 \
  --progress-every 25 \
  --output \
  docs/evaluations/artifacts/SWM25-75_77_300X_OFFLINE_2026-08-13.json
```

runner는 출력 경로가 package 밖이면 실행을 거절하고, story별 check label 중복,
실행 중 source·test 변경도 artifact 생성 전에 fail-fast한다. 또한 Python
assert가 제거되는 optimized 실행을 거절한다. 이번 artifact에는
`assertions_enabled=true`, `python_optimize=0`이 기록됐다.
