2026-09-27

## 2026-10-04: 입력 시각·도착 순서 보완

아래의 9월 27일 결과는 당시 구현·평가 기록이다. 이후 사람 연결에는 다음 조건을 추가했다.

- 원본 촬영 시각이 같은 Pose를 우선한다. 해당 시각에 관측된 빈 결과나 약한 박스를
  주변의 정상 박스로 덮어쓰지 않는다.
- 정확히 같은 시각의 Pose가 없으면 RGB 촬영 시각의 **앞뒤 각각 100ms 이내**에
  실제 Pose 관측이 모두 있어야 한다. Cloud가 지정한 최소 두 이미지에서 모든 이웃 관측이
  동일 트랙·연속성 토큰을 가리키고, 기존 IoU 0.60·차순위 차이 0.15 조건을 통과해야 한다.
  한쪽 관측만으로 위치를 외삽하거나 중간 박스를 만들어 내지 않는다.
- Cloud 요청 때 확보한 관측은 유지하되, 응답까지 늦게 도착한 관측으로 누락 시점을
  다시 확인한다. 현재 시점의 박스를 과거 영상에 대입하지 않는다.
- 요청 중 새 Pose 후보가 생겨도 촬영 구간 안의 첫 후보이며 아직 분석·답변을 받지 않은
  동일 대상이면 이미 받은 Cloud 결과를 재사용한다. 촬영 구간 이후의 새 후보,
  수정·종료·답변 처리된 사건에 오래된 결과를 덮어쓰지 않는다.
- Cloud 응답 후에는 최대 2초 동안 새 Pose 입력 시 미연결 발견을 다시 대조한다.
  동의·설정·연결 세션과 Pose 입력 세대, 현재 대상 연속성, 사건 상태 검사를 유지한다.
  기존의 유효한 사람별 사건에 연결하며, 재대조 자체로 Cloud를 다시 호출하지 않는다.
- 이 방식의 연결 근거는 `association_link.method=measured_pose_timestamps_v1`에
  RGB·Pose 촬영 시각과 함께 남긴다. 영상 추적에 의한 기존
  `continuous_visual_track_pose_v1` 근거와 구분한다. 최초 미연결 기록도 보존한다.

### 응답 후 연결된 장면 사건·질문 정리

- 장면 사건 B의 **모든 발견**이 사람별 사건에 검증된 근거로 연결된 경우에만 B를
  `incident_merged` / `findings_associated`로 닫는다. 정상 판정이 아니다.
  대상 사건 ID를 `mergedIntoIncidentIds`로 저장하고 기존 영상·박스·답변·알림 이력을 남긴다.
- 다른 미확인 발견, 발견 목록 용량 초과, 대상이 불분명한 도움 요청/긴급 알림이 남으면
  B를 유지한다. 재연결 캐시에서 발견이 사라져도 연결 완료로 세지 않는다.
- 사람별 사건 반영·연결 근거·B 병합 이벤트를 SQLite의 한 트랜잭션에 저장한다.
  실패하면 병합 상태나 질문 취소 이벤트를 외부에 노출하지 않는다.
- Coordinator는 B의 질문 대기열을 제거하고, 이미 요청/진행 중이면 Manager에 취소를 보낸다.
  취소 접수만으로 다음 질문을 시작하지 않고 기존 mission의 종료 결과를 기다린다.
  종료 확인 실패 시 새 질문은 대기한다(`confirmation_merge_cancel_unconfirmed`).
  이미 발화한 질문을 되돌리는 기능은 아니며, 기존 장면의 늦은 결과를 사람의 답으로 옮기지 않는다.
- 병합 종료 이벤트도 주기적으로 재전달해 유실·Coordinator 재시작 뒤 오래된 질문이 부활하지
  않도록 한다. 기존 사람별 질문 ID는 유지하고, 연결을 위한 추가 Cloud 호출은 하지 않는다.
- SWM25-194의 진행 중 대화 보존과 함께 적용한다. 사람별 사건에 새 근거가 들어와도
  진행 중인 질문은 원래 근거 버전으로 유지한다. 기존 답변은 그 질문에만 반영하고
  이후 근거를 정상으로 처리하지 않는다. 반면 모든 발견이 연결되어 병합 완료된
  장면 질문은 종료 대상으로 구분하며, 그 늦은 답변을 대상 사람에게 전달하지 않는다.
- 웹은 B를 ‘다른 사건에 병합됨’으로 표시하고 연결된 사건으로 이동할 수 있게 한다.
  B는 정상 목록이 아니라 처리 완료 목록에 남고, 중복 확인 필요 표시·로봇 재발신에서 제외한다.
  사용자가 명시적으로 다시 연 사건은 기존 검토 규칙을 유지한다.
- 새 이벤트 계약이므로 **웹 서버/화면 → 로봇 런타임·Coordinator 함께** 배포한다.
  예전 서버에는 새 이벤트를 보내지 않는다. 운영 배포는 별도다.

`test_fall_scene_merge.py`, `test_fall_timing_handoff.py`는 사건/질문 수, 다인 부분 연결,
캐시 유실, 도움 요청 보존, 대기/진행/접수 전 질문 취소, 늦은 결과 차단을 검증한다.
가짜 mission future를 사용한 취소 시험은 실제 마이크·스피커의 종료를 검증한 것은 아니다.
기존 실기 사례처럼 Pose 박스가 끝내 없으면 이 수정만으로 사람 연결이 가능해지지 않는다.

## 9월 27일 기준 및 당시 결과 (이하 과거 기록)

한 경로에서 낙상을 의심하면 확인을 시작한다. 다른 경로와의 연결 성공을 기다려
발견을 버리거나 정상으로 바꾸지 않는다. 병합은 같은 사람이라는 근거와 기존 사건의
시간·진행 상태·추적 연속성을 확인한 경우에만 진행한다.

현재는 다음처럼 **확인할 수 있는 관측 상태**를 나눈다.

| 구분 | 기록 값 | 실제로 확인한 것 | 처리 |
|---|---|---|---|
| 비교할 유효한 Pose 관측이 없음 | `pose_evidence_missing` | 비교 시점에 연결용 Pose 박스·연속성 토큰이 없음 | Cloud 발견을 별도로 기록하고 대상 미확인 장면 확인 유지 |
| Pose 관측은 있지만 대상 연결 미확인 | `identity_unverified` | 일부 Pose 관측은 있으나 같은 대상·사건으로 연결하는 조건을 통과하지 못함 | 상세 실패 이유를 남기고 별도 확인 유지. 억지 병합 금지 |

이미 연결된 결과는 `matched`로 기록한다. 과거 기록처럼 관측 정보를 갖고 있지 않은
경우는 `unknown`이며 위 두 경우 중 하나로 추측해 채우지 않는다.

`identity_unverified`는 **두 경로가 같은 사람을 찾았다는 뜻이 아니다.** Pose가 옆의
돕는 사람만 찾았을 수도 있고 Cloud 위치가 틀렸을 수도 있다. SYN063은 검수자가 보면
누운 사람의 Pose가 없지만, 시스템에는 돕는 사람의 Pose가 있으므로 이 경우로 남는다.
그를 누운 사람의 ID로 대신 연결하지 않는다.

`pose_evidence_missing`도 사람이 없다는 뜻은 아니다. 약한 관측만 있거나, 입력이 없거나,
해당 이미지와 시각을 맞출 수 없는 경우를 포함한다. 박스가 조금 겹친다는 이유로
약한 Pose를 유효한 관측으로 승격하지 않는다.

## 이번에 바꾼 코드

- 기존 `association_status`와 상세 `reason`은 유지하고 발견 메타데이터에
  `association_case`, `association_evidence`를 추가했다.
- 관측 정보는 Cloud 요청을 보낼 때 고정한 Pose 스냅샷으로 계산한다.
  늦게 도착한 응답에 현재의 다른 사람 박스를 끼워 넣지 않는다.
- `association_evidence`에는 비교 범위(`scope`), 이미지 수(`samples`),
  Pose 박스가 있는 이미지 수(`pose_box_samples`), 연결용 Pose 관측이 있는 이미지 수
  (`usable_pose_samples`)를 기록한다. 이는 사람 수가 아니라 이미지 시점 수다.
- Cloud가 위치를 준 경우에는 그 위치가 가리키는 이미지들만 센다(`finding_frames`).
  위치가 없으면 요청 구간 전체의 관측 유무만 센다(`request_window`). 위치를 복원하거나
  사람을 연결한 것으로 처리하지 않는다. 잘못된 이미지 참조는
  `invalid_sample_reference`로 남기고 관측 부재라고 단정하지 않는다.
- 하나라도 연결용 Pose 관측이 있으면 연결 실패를 `identity_unverified`로 남긴다.
  모든 시점의 관측이 충분한지는 기존 위치·추적 연속성 검사에서 별도로 확인한다.
- 메타데이터는 로컬 SQLite 발견 기록과 런타임 발견 이벤트에 포함한다.
  JSON 필드 추가이며 DB 테이블 변경·운영 서버 배포·웹 표시 변경은 하지 않았다.
- 미연결 두 경우 모두 기존 장면 사건과 일반 확인 질문 경로를 사용한다.
  분류를 위해 추가 Cloud 요청을 만들거나 새로운 질문을 더하지 않는다.
- Pose 단독 후보는 기존처럼 Cloud의 판정을 기다리지 않고 사람별 사건을 생성한다.
  음성 질문의 시작 시점과 조건은 기존 Pose 분석 경로를 유지한다. 이번에
  모든 Pose 후보의 음성 질문을 즉시 병렬 실행하도록 변경한 것은 아니다.

## 유지한 안전 조건

- 유효한 Cloud 의심이면 Pose 연결 없이도 장면 확인을 시작한다.
- 같은 장면의 반복 발견은 기존 확인에 보관한다. 사람 신원이 같다고 합친 것은 아니다.
- 정상·판단 불가·응답 전체 오류를 새로운 의심 신호로 바꾸지 않는다.
- 장면의 정상 답변이나 대상과 연결하지 못한 사람의 “괜찮다” 답변으로 미확인 사건을 닫지 않는다.
- 이후 Pose가 나타나도 이전 Cloud 사건과 자동으로 같은 사람이라고 간주하지 않는다.
- 이미 연결 가능한 Cloud 발견은 기존 기하·토큰·현재 관측·사건 변경 검사 후 사람별 사건에 반영한다.
- 설정 철회, 오래된 답변, 처리 중 사건 변경, 저장 실패, 용량 상한의 기존 처리를 유지한다.
